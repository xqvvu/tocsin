# 通知目标对话框页脚可见性

## 状态

- 状态：已实现（第 51 轮回归修复）
- 范围：通知目标编辑对话框、通知目标新建对话框
- 迁移：无

## 问题

`REQ-196` 在通知目标编辑对话框中加入了「排队投递会读取最新配置」的提示
（`apps/console/src/features/destinations/ui/destination-edit-dialog.tsx:99-103`）。
该提示位于对话框标题与表单之间，但表单仍使用一个只扣除固定标题高度的最大高度：

- 表单容器：`max-h-[calc(min(760px,calc(100dvh-2rem))-6rem)] overflow-hidden`
  （`apps/console/src/features/destinations/ui/destination-form.tsx:1053-1059`）。
- 对话框外壳：`max-h-[min(760px,calc(100dvh-2rem))] overflow-hidden` 的纵向 flex
  （`apps/console/src/components/common/configuration-dialog-content.tsx:13`）。

提示出现后，标题 + 提示 + 表单的总高度超过外壳上限，而外壳又是 `overflow-hidden`，
于是表单底部的「取消 / 预览 / 保存通知目标」被裁到弹窗之外，且没有任何错误提示。
浏览器实测（1280x900 与 390x844）确认：只要该目标有排队投递，保存按钮就完全不可见、
不可点击；临时隐藏提示后按钮立即回到弹窗内。

这直接卡住故障或补投期间的目标配置修改，是本轮发现的最高影响缺陷。

## 用户故事

作为值班 SRE，当我在故障处理中编辑通知目标时，无论队列里有多少条待投递、无论窗口
宽度如何，我都希望「保存通知目标」和「预览」始终可见可点，而不是被提示挤出弹窗。

## 范围

- 通知目标表单在对话框布局下改为消费对话框的剩余空间：
  `min-h-0 flex-1 overflow-hidden`，不再使用扣除固定标题高度的 `max-h`。
- 编辑对话框外壳从「仅 `max-h` 的自动高度」改为确定高度
  `h-[min(760px,calc(100dvh-2rem))]`。仅有 `max-h` 时外壳高度仍由内容决定，
  `flex-1` 表单不会收缩，页脚依旧会被裁切；确定高度后表单才能获得可收缩的
  可用空间。新建对话框保持自动高度（其内容未超高）。
- 表单内部滚动区保持唯一的 `overflow-y-auto` 区域，页脚保持 `shrink-0` 且位于滚动区之外。
- 排队投递提示容器标记 `shrink-0`，空间紧张时提示不被压缩。
- 新建通知目标对话框复用同一表单布局，需一并保持页脚可见。
- 增加结构回归测试：对话框布局下表单必须是 flex 消费方、页脚在滚动区之外且
  `shrink-0`，编辑对话框外壳必须带确定高度。

## 非目标

- 不改变排队投递提示的文案、查询、缓存或显示条件。
- 不调整对话框最大高度、宽度或断点。
- 不修改其他表单（告警源、路由、静默规则）的布局。
- 无 schema、迁移、oRPC、service 或依赖改动。

## 验收标准

1. 目标存在排队投递时，1280x900 与 390x844 下编辑对话框的「取消 / 预览 / 保存通知目标」
   全部位于弹窗内，可见且可点击。
2. 排队投递为 0 时提示不渲染，页脚同样可见。
3. 新建目标对话框在两种视口下页脚可见。
4. 表单内容较长时只在表单内部滚动，页脚保持固定。
5. 结构回归测试覆盖：表单为 `flex-1` / `min-h-0`、不含固定 `max-h`、滚动区包含
   `overflow-y-auto`、页脚为滚动区之外的 `shrink-0` 元素。

## 架构边界

- 纯前端布局修复，位于 `features/destinations/ui/`。
- 不新增组件、状态、查询或服务端契约；`components/ui` 与 `components/common` 不变。
