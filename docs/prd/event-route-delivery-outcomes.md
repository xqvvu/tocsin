# 事件详情：按路由显示投递结果

状态：已实现。

## 问题

事件详情的「路由匹配」标签页只显示每条路由命中了几个通知目标，投递结果在另一个
「事件投递」标签页里。值班工程师排查「这条路由到底发出去了没有」时，必须在两个标签页
之间靠记忆对照路由名与目标名，告警风暴或路由较多时很容易看错。

代码现状：

- 路由匹配表只渲染 `destinationIds.length`（`event-detail-route-matches-table.tsx`）。
- 投递表逐条显示目标、路由、状态，但不按路由聚合
  （`event-detail-deliveries-table.tsx`）。
- `EventDetailDelivery` 已带 `routeId` 与 `state`，无需新增 DTO 或查询。

## 用户故事

作为值班工程师，我在事件详情里看到一条路由命中后，希望同一行直接告诉我这条路由的成功、
失败、排队中投递数量，这样不用切标签页就能判断是「没匹配」还是「匹配了但没发出去」。

## 范围

- 在「路由匹配」表新增「投递结果」列。
- 按 `deliveries[].routeId` 聚合，按生命周期顺序展示非零状态徽标：
  成功、失败、运行中、待处理、已抑制。
- 命中但没有任何投递时显示「无投递」；未命中路由显示「未命中」。
- 手工补投产生的投递 `routeId` 为 `null`，不计入任何路由。
- 中英文案同步。

## 非目标

- 不新增 oRPC 过程、DTO 字段或 SQL 查询。
- 不改变路由匹配、投递、重试或抑制语义。
- 不把投递表替换为按路由分组的视图；逐条投递仍保留在「事件投递」标签页。

## 验收标准

1. 一条路由有 2 条成功、1 条失败投递时，该行显示「成功 2」「失败 1」。
2. 命中但无投递的路由显示「无投递」。
3. 未命中的路由显示「未命中」，不显示「无投递」。
4. 仅有 `routeId = null` 的手工投递时，路由行仍显示「无投递」。
5. 状态数量与「事件投递」标签页的同一批行一致。
6. `vp check` 0 errors，相关测试通过。

## 架构边界

- 纯前端：`features/events/ui` 内的派生函数与展示组件。
- 复用 `EventDetail` 现有 `deliveries` 字段，不触碰服务端、仓储、contract 或迁移。
- 聚合函数为纯函数，便于单测覆盖。
