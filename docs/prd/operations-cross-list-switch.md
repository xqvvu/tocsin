# 事件与投递按同条件切换

- 状态：已实现（REQ-233）
- 来源：自主迭代 requirements 车道（第 85 轮），第 184 轮交付
- 关联：`docs/prd/operation-search-identifiers.md`、`docs/prd/operation-search-labels.md`

## 问题

事件列表与投递列表共用同一套 URL 筛选模型，但值班工程师排查一次告警时，往往先在事件列表按
告警源、级别、状态和时间窗口定位问题，再想查看这些告警实际产生了哪些投递。侧栏在两个列表之间
切换时不带任何条件，工程师必须在投递列表重新选一遍同一组筛选，或者丢失时间窗口后从头找。

现有筛选面板已经明确区分两页的能力：目的目标匹配、投递结果、解析失败是事件页独有；路由、
目标类型、回执、投递状态、尝试次数、最近响应状态类别、时间口径是投递页独有。因此不能简单
整组搬运，否则会把对端页面不理解的条件带过去，或让同一个键在对端产生不同含义。

## 用户故事

作为值班工程师，我在事件列表用「告警源 + 级别 + 时间窗口」缩小到一次故障后，希望能一键打开
投递列表并保留这组条件，直接看到这些事件的通知结果；反之，在投递列表定位到一批失败投递后，
也能一键回到事件列表查看对应的告警内容。

## 范围

- 两页工具栏各增加一个跨列表动作：
  - 事件页：「查看同条件投递」，跳转 `/deliveries`；
  - 投递页：「查看同条件事件」，跳转 `/events`。
- 只携带两页语义一致的键：`sourceId`、`severity`、`status`、`q`、`fingerprint`、
  `range`、`rangeAnchor`。
- 丢弃目标、目标匹配/结果、解析失败、路由、目标类型、事件 id、回执、投递状态、尝试次数、
  最近响应状态类别、时间口径，以及两页各自的页码和 `rangeUntil` 分页快照。
- 没有可携带的共有条件时不渲染该动作，避免与侧栏链接重复并让「同条件」文案失真。
- 时间窗口连同 `rangeAnchor` 一起携带，保证对端看到的是同一个下界。

## 非目标

- 不改变侧栏导航行为，侧栏切页仍然不保留条件。
- 不做跨实体合并页或全局筛选记忆（REQ-205）。
- 不新增服务端端点或查询参数；复用现有 `DashboardOperationSearchSchema`。
- 不做自动刷新（REQ-35）。

## 验收标准

1. 事件页存在共有条件时显示「查看同条件投递」，点击后 URL 只包含共有键，投递列表按同一组
   条件请求，页码从第 1 页开始。
2. 投递页存在共有条件时显示「查看同条件事件」，点击后 URL 只包含共有键，事件列表按同一组
   条件请求，页码从第 1 页开始。
3. 只有单页独有条件（例如仅 `routeId`、仅 `deliveryState`、仅 `destinationKind`）时两个动作
   都不出现。
4. 仅有时间窗口时，`range` 与 `rangeAnchor` 一并保留；仅有 `rangeAnchor` 而没有 `range` 时
   不写入 URL。
5. 中文文案沿用 SRE 术语：「告警源」「级别」「状态」「指纹」「时间窗口」「投递」「事件」。

## 架构边界

- 共有键的裁剪是纯函数，放在 `features/operations/model/operation-search.ts`，与
  `pruneSearch` / `mergeOperationSearch` 同层，便于单测且不依赖路由。
- 两个工具栏保持展示型组件：通过 `onViewDeliveries` / `onViewEvents` 回调接收动作，
  由页面用已注入的 `navigate` 执行跳转，工具栏不直接依赖 Router。
- 无服务端改动、无 schema 迁移、无新依赖。
