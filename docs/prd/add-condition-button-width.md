# 路由与静默表单的「添加条件」按钮不再被拉伸成整行

- 状态：已实现（第 109 轮）
- 来源：UI 评审发现（第 109 轮浏览器实测，截图
  `/tmp/tocsin-ui-109-route-dialog-1440.png`、`/tmp/tocsin-ui-109-route-dialog-390.png`）
- 关联：`apps/console/src/features/routes/ui/route-forms.tsx`、
  `apps/console/src/features/suppressions/ui/suppression-forms.tsx`、
  `apps/console/src/components/ui/field.tsx`

## 问题

`Field` 的垂直布局变体给所有直接子元素强制 `width: 100%`
（`components/ui/field.tsx:55` 的 `*:w-full`）。「添加条件」按钮是 `Field` 的直接子元素，
按钮自身的 `w-fit` 被这条后代变体规则覆盖，于是渲染成一条整行宽、带边框的空白条：

- 新建/编辑路由弹窗中，告警源、严重程度、状态、标签、标题包含、消息包含六个条件区各有一条；
- 静默规则表单的文本条件与标签条件也使用同样的结构，同样受影响。

运维视角下，这条通栏空白条看起来像一个需要填写的空输入框，真正可点的「＋ 添加条件」
反而缩在中间，容易被误认为表单未加载完成。390px 宽度下同样成立。

## 用户故事

作为值班运维，我在新建路由或静默规则时，希望「添加条件」是一个尺寸正常的次要按钮，
而不是一条看起来像空输入框的整行色块，这样我能一眼看出该点哪里继续添加条件。

## 范围

- 在 `ConditionList`（路由）与两个条件列表（静默：文本条件、标签条件）中，把「添加条件」
  按钮包进一个普通 `div` 容器，让容器的全宽由 `Field` 规则接管，按钮保持自身内容宽度。
- 增加结构回归测试：断言「添加条件」按钮不是 `[data-slot="field"]` 的直接子元素。
  jsdom 不计算 Tailwind 样式，因此以 DOM 结构固定住这条约束。
- 不改 `Field` 原语自身的 `*:w-full` 规则：它服务于普通输入控件的全宽布局。

## 非目标

- 不调整表单其它间距、字号、按钮变体。
- 不改变条件行的增删逻辑、校验或提交语义。
- 不改变路由弹窗宽度（另见 backlog UI-NEW-113）。
- 不引入新依赖、不改 i18n 文案、不改服务端契约。

## 验收标准

1. 路由新建/编辑弹窗中，六个「添加条件」按钮均为内容宽度，不再渲染成整行空白条。
2. 静默规则表单的文本条件与标签条件同样恢复正常尺寸。
3. 点击「添加条件」仍能新增一行条件。
4. 新增结构测试覆盖路由与静默两个表单，且既有测试保持通过。
5. `vp check`、`vp run -r test`、`vp run -r build` 通过；浏览器在 1440×900 与 390×844
   各复看一次路由新增弹窗。

## 架构边界

- 改动只在 `features/routes/ui`、`features/suppressions/ui` 的展示层与对应组件测试。
- 不触碰 oRPC contract、service、repository、SQLite schema、auth。
- 无迁移、无新依赖、无环境变量变化；回滚只需还原两个组件文件与其测试。
