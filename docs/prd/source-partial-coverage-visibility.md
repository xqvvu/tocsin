# 告警源部分路由受阻的可见性

- 状态：已实现（2026-10-21，第 57 轮）
- 来源：UI 评审发现 UI-13；浏览器实测复现
- 相关：REQ-129（告警源覆盖率按可投递性计算）、REQ-138（目标侧覆盖率）

## 问题

告警源列表的「路由覆盖」单元格只有在**全部**匹配路由的目标都停用时，才会显示
「目标全停用」；一旦至少有一条路由可投递，徽标就只显示可投递条数。被目标停用挡住的
其余路由只写进原生 `title`，触屏、键盘聚焦与读屏用户都看不到。

实测（`/sources`，1280×900）：2 条启用路由中 1 条因目标停用不可投递，单元格仍显示
「1 条可投递」，界面没有任何受阻信号。值班人员会误以为该告警源的路由全部通畅。
证据：`apps/console/src/features/sources/ui/source-route-coverage-cell.tsx:19-27`
（徽标只渲染可投递数）、`:48-53`（受阻原因只进 `title`）。

## 用户故事

作为值班工程师，我在告警源列表扫视时，需要直接看出「这个源有几条路由能投递、几条被
挡住」，而不是逐行悬停，避免把部分受阻误判为全部通畅。

## 范围

- 当 `deliverableRouteCount > 0 && blockedRouteCount > 0` 时，徽标文案显示
  「{deliverable}/{enabled} 条可投递」，例如「1/2 条可投递」。
- 保留既有 `title` 中的阻断路由名单，作为明细补充。
- 新增中英文 i18n 键 `sources.table.routes.partialDeliverable`。
- 全可投递、全部受阻、未匹配路由三种既有分支不变。

## 非目标

- 不改变覆盖率计算口径（`sourceRouteCoverage` 仍以「至少一个启用目标」判定可投递）。
- 不新增路由级明细弹层，不改表格列宽或移动端布局（见 UI-25 / UI-23）。
- 不涉及服务端、DTO、持久化或迁移。

## 验收标准

- [x] 部分受阻时列表徽标显示「1/2 条可投递」，无需悬停即可看到受阻份额。
- [x] 全可投递时仍显示「2 条可投递」，不出现分母。
- [x] `title` 仍包含受阻路由数量与名单。
- [x] 中英文案齐全，中文使用「可投递」这一既有 SRE 术语。
- [x] 组件测试覆盖部分受阻与全可投递两个分支；列表集成测试同步更新。

## 架构边界

纯前端展示改动，位于 `features/sources/ui`；数据来自既有
`SourceRouteCoverage`（`features/sources/model/source-route-coverage.ts`），
不新增查询、不触碰 `/routes` 与 `/suppressions` 的内联编辑代码。
