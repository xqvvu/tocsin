# 告警静默列表筛选与顶栏下钻

- 状态：已交付（第 145 轮）
- 关联：REQ-285（本切片），REQ-2（并入本切片）
- 证据：`apps/console/src/features/suppressions/ui/suppressions-section.tsx`（筛选前只有表格与排序）、
  `apps/console/src/features/suppressions/ui/active-suppression-indicator.tsx`（徽标原样落到全量列表）

## 问题

`/suppressions` 是值班同学确认「现在到底有没有东西在压着告警」的唯一入口，但它只能看全量列表：

- 规则一多，生效中的规则虽然按运营优先级排在最前，operator 仍要翻页才能确认某类规则
  （例如「这次变更相关的维护时段」「某个告警源上的临时静默」）是否存在。
- 顶栏的静默徽标只说明「有 N 条规则在生效」，点击后落到全量列表，第一页可能被已停用或已结束的规则占据。
- 现有的 Events / Deliveries 列表都有关键字与状态筛选，静默列表是唯一没有筛选能力的运维列表，
  操作形态不一致。

## 用户故事

1. 作为值班工程师，我想按生命周期状态（生效中 / 待开始 / 已结束 / 已关闭）筛选规则，
   以便快速确认当前是否还有维护时段在压着告警。
2. 作为值班工程师，我想按用途（临时静默 / 维护时段）和关键字（规则名称、原因、匹配条件、
   关联的告警源与通知目标名称）搜索，以便在几十条规则里定位与本次事件相关的那一条。
3. 作为值班工程师，我从顶栏静默徽标点进来时，希望直接看到「正在生效」的规则，
   而不是先看一页已经结束的规则。
4. 作为值班工程师，筛选后没有结果时，我希望明确知道是「筛选没命中」而不是「规则不存在」，
   并能一键清空筛选。

## 范围

- `/suppressions` 路由新增 URL 搜索参数：`state`、`kind`、`q`；非法值回退为「不限」，不报错。
- 纯客户端过滤（列表本就整表加载、客户端分页），派生状态复用 `suppressionStateAt`，
  不新增存储列、不改 `suppressions.list` 契约。
- 过滤器工具栏：关键字输入（300ms 防抖后写入 URL）、状态下拉、用途下拉、已选条件 chip、一键清空。
- 关键字匹配：规则名称、原因、用途原始值、指纹、标签键值、标题/内容包含、严重级别、状态，
  以及解析后的告警源 / 通知目标名称；空格分隔的多个词需全部命中。
- 空态区分：无规则（原有空态）与「当前筛选没有匹配」（新空态 + 清空按钮）。
- 顶栏静默徽标链接到 `?state=active`。
- 中文文案按 SRE 术语（告警源、通知目标、维护时段、临时静默），中英文同步。

## 非目标

- 服务端筛选、分页或契约变更（规则数量级不需要）。
- 批量启停、排序偏好、保存筛选视图。
- 详情页筛选或命中记录筛选。

## 验收标准

- `state` 筛选使用调用方时钟的派生状态；`disabled` 优先于 `expired`。
- 关键字大小写不敏感；多个词 AND；能通过告警源 / 通知目标名称命中规则。
- URL 为空时不写空参数；手改 URL 的非法 `state` / `kind` 回退为「不限」而不是抛错。
- 筛选无结果时显示「没有符合条件的规则」，点击清空恢复全量；清空会同时取消未提交的关键字草稿。
- 顶栏徽标 href 带 `state=active`。
- 单元测试覆盖过滤模型、URL 剪裁与合并、过滤器交互、两种空态；原有静默测试不回归。

## 架构边界

- 过滤模型是 `features/suppressions/model/suppression-search.ts` 中的纯函数，环境中立，
  不导入 `#/server/*`、`#/infra/*` 或浏览器全局。
- URL 解析与写回只在路由文件 `routes/_dashboard.suppressions.tsx`；页面组件通过 props 接收
  `search` 与 `onSearchChange`。
- 防抖草稿钩子抽到 `components/common/use-debounced-search-draft.ts`，由 Events / Deliveries
  过滤器与静默过滤器共用，行为与原有实现一致。
- 不新增依赖、不改数据库、不改投递 / 路由 / 鉴权语义。
