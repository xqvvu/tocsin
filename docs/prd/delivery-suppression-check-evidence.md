# 投递详情的静默判定逐项证据

## 状态

已实现（2026-10-21，第 49 轮迭代）。

## 问题

投递被静默规则拦下后，详情页只展示一条英文原因快照和规则链接：

- 原因快照来自 `suppressReason`，是抑制发生时写入的一句话（`delivery.ts:24-35`）。
- 运维想知道「到底是哪一条条件命中了这条告警」，只能跳到静默规则详情页，
  再自己把规则条件和事件的严重程度、状态、标签、标题逐项对照。
- PRD 已承诺抑制判定包含逐项 checks（`docs/prd/alert-suppression.md:72,111-121`），
  core 也已返回 `SuppressionMatchResult.checks`（`packages/core/src/suppression/suppression.ts:165-170,186-218`），
  但 console 从未消费它。

值班切换期间最常问的两个问题是「为什么没发」和「它命中了哪条规则」。第二个问题
现在要跨两个页面手工比对，排障成本高，也容易把「规则后来改过」误判成「当时就没命中」。

## 用户故事

作为值班 SRE，我打开一条被抑制的投递，希望直接看到静默规则对这条事件的逐项判定
（告警源、严重程度、状态、标签、标题、消息、通知目标、Fingerprint），
这样不用离开投递详情就能确认「为什么被拦下」。

## 范围

- 在投递详情的静默提示（`DeliverySuppressionNotice`）内新增逐项判定区块。
- 规则仍存在时，按**当前规则**重算 `evaluateSuppressionMatch`，复用现有的
  `RouteMatchCheckBadges` 渲染证据，保证与路由匹配证据的措辞一致。
- 明确标注「按当前规则重算」，并在当前规则已不匹配时提示「投递是在当时生效的规则下被抑制」，
  避免把重算结果误当成抑制时刻的审计记录。
- 规则已被删除（`suppressionId` 为空）时保持现状：只显示原因快照，不显示 checks。
- 规则查询失败或加载中时不渲染 checks，不影响原因快照与规则链接。

## 非目标

- 不新增投递列或迁移，不保存抑制时刻的 checks 快照。
- 不改静默判定语义、投递语义或 oRPC contract。
- 不在投递列表批量展示判定证据。
- 不重做静默提示的整体视觉。

## 验收标准

1. 被抑制且规则仍存在的投递详情，在原因快照下方显示「匹配条件（当前规则）」标题、
   命中/未命中徽标和逐项条件徽标。
2. 当前规则不再匹配该事件时，显示「未命中」和「当前规则已不再匹配该事件」的说明。
3. 规则已删除时，只显示原因快照与「规则已不存在」提示，不发起规则查询。
4. 规则查询失败时，不渲染 checks 区块，也不阻塞页面其他内容。
5. 中英文文案齐全，中文使用 SRE 术语；组件测试覆盖匹配、规则变更、规则缺失、查询失败。

## 架构边界

- 纯前端只读投影：`features/deliveries/ui/delivery-suppression-checks.tsx`。
- 判定复用 `@tocsin/core` 的 `evaluateSuppressionMatch`，不重新实现比较逻辑。
- 证据渲染复用 `features/routes/ui/route-match-check-badges.tsx`。
- 规则数据通过现有 `suppressionQueryOptions` 读取，不新增服务端接口。
- 无 schema、无迁移、无投递语义变化。
