# 删除前展示历史影响面（REQ-268）

## 问题

告警源、路由和通知目标的删除是硬删除：SQLite 外键级联会一并删掉事件、投递、投递尝试和
加急呼叫记录（`apps/console/src/infra/sqlite/migrate/schema.ts:65-66,114-119,143,165-197,228-229`）。
现有确认对话框只说明「相关投递也会级联删除」，既不给数量，也不给事件/尝试/加急的拆分；
告警源与目标还会在客户端计算路由收窄/连带删除（`apps/console/src/features/routes/model/route-reference-impact.ts:15-43`），
但完全看不到历史数据规模。运维在凌晨清理一条误配置的告警源时，无法判断这一下会销毁
多少排障证据。

`docs/prd/post-mvp-planning.md:49-59` 明确当前内测采用硬删除语义，并要求第一次公开
release 前重新评估；在重新评估之前，至少要让删除的破坏面可见并被显式确认。

## 用户故事

作为值班运维，我在删除告警源 / 路由 / 通知目标前，希望看到这次删除会销毁多少历史记录，
并且只在明确确认后才执行，这样我不会因为一次误点丢掉整段故障的排障证据。

## 范围

- 新增只读预览：`sources.previewDelete`、`routes.previewDelete`、`destinations.previewDelete`，
  入参复用既有 `Delete*CommandSchema`，输出统一的删除影响面 DTO：
  `eventCount`、`deliveryCount`、`attemptCount`、`oncallPingCount`。
- 计数在服务端按删除时实际生效的外键级联路径统计：
  - 告警源：`events.source_id` 及其下游投递、尝试、加急记录；路由引用清理沿用既有
    客户端展示（`routeReferenceImpact`）。
  - 路由：`deliveries.route_id` 及其下游尝试、加急记录；事件保留。
  - 通知目标：`deliveries.destination_id` 及其下游尝试、加急记录；事件保留。
- 三个删除对话框在打开时拉取预览，展示分项计数；历史记录总数大于 0 时，删除按钮
  保持禁用，直到运维勾选「我确认一并删除这些历史记录」。
- 预览读取失败时展示错误提示，但仍允许删除：预览是决策辅助，不是删除的前置凭据，
  不能因为读不到计数就把运维锁死在无法清理配置的状态。

## 非目标

- 不改变硬删除语义、级联范围或数据库结构；不引入软删除/归档。
- 不保存删除审计记录，不做删除历史页面。
- 不在列表页批量展示每条配置的历史体量（避免为列表增加 N 次计数查询）。
- 不改动路由影响面的既有文案与计算方式。

## 验收标准

1. 管理员打开告警源删除对话框时，服务端返回该告警源名下的事件、投递、尝试、加急计数；
   有历史时删除按钮禁用，勾选确认后可用。
2. 路由与通知目标对话框同理；路由预览不把事件计入（事件保留），目标预览不把事件计入。
3. 预览不存在的实体返回 `NOT_FOUND`，与删除行为一致。
4. 没有历史记录时，对话框不显示确认勾选，删除流程与现状一致。
5. 预览失败时显示可读错误，删除按钮保持可用（不因统计失败阻断清理）。
6. 仓储计数与真实级联结果一致：删除后事件/投递/尝试/加急行数减少的数量等于预览值。
7. 中英文文案齐全，`messages.test.ts` 键齐全；删除确认按钮的可访问名称不变。

## 架构边界

- 共享 DTO 与 schema 放在 `@tocsin/core` 的 configuration 结果模块。
- 计数查询属于历史读模型，放在 `history` 仓储（`countDeletionImpact`），不散落到服务或路由。
- 服务只做存在性校验与委派；oRPC 路由保持薄，沿用 `withDashboardService`。
- 浏览器只通过 `#/lib/orpc` 调用预览；不新增前端 DI 或全局状态。
- 无 schema 变更、无迁移、无新依赖，可整片回滚。
