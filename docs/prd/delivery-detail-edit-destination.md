# 投递详情内修复目标配置

> 状态：已实现（2026-10-22 核实：`delivery-destination-edit-action.tsx` 已挂载编辑入口）。
> 以下「问题」节为实现前的历史背景。

## 问题

投递失败后，值班工程师通常已经知道问题出在目标配置上（Webhook URL 写错、签名密钥轮换、飞书群
`chat_id` 变更、通知目标被停用等）。当前的排障闭环是断开的：

- 投递详情页工具栏只有「重试投递」和「返回投递列表」
  （`apps/console/src/features/deliveries/ui/delivery-detail-page.tsx:56-66`）；
- 目标编辑入口只在「通知目标」列表页，且需要先找到同一个目标再打开对话框
  （`apps/console/src/features/destinations/ui/destinations-page.tsx:221-252`、
  `apps/console/src/features/destinations/ui/destination-actions.tsx:85-95`）；
- 从详情页跳到列表页再回来，原来的筛选、滚动位置和上下文全部丢失，排障节奏被打断。

结果是：一个本可以「看一眼失败原因 → 修配置 → 重试」的动作，被迫变成跨页面往返。

## 用户故事

作为正在处理失败投递的值班 SRE，我希望在投递详情页直接打开当前通知目标的编辑对话框，
改完配置保存后留在原页面并立即重试，以便不离开失败现场就完成修复闭环。

## 范围

- 投递详情工具栏在投递状态为 `failed` 时新增「编辑目标」动作。
- 复用现有 `DestinationEditDialog`（含模板草稿、密钥 preserve/replace 语义、预览）。
- 新增一个轻量的目标编辑加载器，按需拉取通知目标列表、目标目录与飞书应用列表，
  仅在对话框打开时请求。
- 保存成功后失效通知目标/路由查询，并失效当前投递详情查询，使详情页立即反映新配置。
- 预览与历史事件样例沿用「通知目标」页的行为，保证两个入口看到同一份渲染结果。
- 中文与英文文案、组件测试。

## 非目标

- 不自动重试。重试仍由操作者显式点击「重试投递」触发（与 AGENTS.md 对投递类动作必须显式的要求一致）。
- 不新增 oRPC procedure、不修改投递/路由/鉴权语义、不做数据库迁移。
- 不把编辑入口扩散到事件详情或投递列表；本切片只解决失败投递详情这一个入口。
- 不重构「通知目标」页现有的预览/编辑状态管理。

## 验收标准

1. 打开一条 `state = failed` 的投递详情，工具栏出现「编辑目标」；`succeeded` 等其他状态不出现。
2. 点击后打开与「通知目标」页一致的编辑对话框，字段预填当前目标配置，密钥字段保持留空即保留。
3. 对话框内「预览」返回与「通知目标」页一致的预览结果，并支持切换历史事件样例。
4. 保存成功后对话框关闭，投递详情自动刷新（目标名称/配置变化可见），「重试投递」仍可用。
5. 目标已被删除或加载失败时，对话框内给出明确说明与重试/关闭入口，不出现空白弹窗。
6. `vp check`、`vp run -r test`、`vp run -r build` 通过；新增组件测试覆盖可见性与打开行为。

## 架构边界

- 纯前端切片：新增组件位于 `apps/console/src/features/destinations/ui/`（目标域）与
  `apps/console/src/features/deliveries/ui/`（投递域），数据通过既有 TanStack Query
  `queryOptions` 与 oRPC 客户端获取。
- 不引入新依赖、不新增服务、不触碰 SQLite；密钥仍由服务端保留，编辑框只提交替换值。
- 投递域对目标域的依赖是单向的（投递 → 目标），目标域不反向依赖投递域。
