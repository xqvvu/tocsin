# 电话加急失败原因可完整查看

> 状态：已交付。以下「问题」段保留交付前的现状记录。

## 问题

投递详情的「电话加急」表格每通呼叫只占一行，`lastError` 用 `truncate` 压成一行
（`apps/console/src/features/deliveries/ui/delivery-pings-table.tsx`）。飞书加急失败时返回的错误
往往带调用链、错误码与请求上下文，值班者在表格里只能看到开头几十个字符，既读不全也无法复制到工单。
同一页面的「投递尝试」表已经用 `DeliveryAttemptDetailDialog` 解决了同类问题，而呼叫记录没有对应入口。

影响：加急失败是 P1 场景，值班者需要把完整错误贴进故障群或工单；当前只能去翻服务日志或直接查库，
排障路径被拉长。

## 用户故事

作为值班工程师，当一通电话加急失败时，我希望在投递详情里直接展开这通呼叫的完整错误并一键复制，
以便判断是接收人不可用、应用权限不足还是飞书侧限流，并把原文交给下游处理。

## 范围

- 投递详情「电话加急」表：错误单元格在存在 `lastError` 时变为可点击触发器，打开详情对话框。
- 对话框展示：呼叫对象、状态、触发方式（含手动发起人）、尝试次数、创建/呼叫/下次重试时间，
  以及完整错误文本；错误文本提供复制按钮。
- 无错误时保持现状：单元格显示共享占位符，不渲染触发器。
- 新增中英文 i18n 文案（`deliveries.detail.pingDialog.*`）。

## 非目标

- 不新增 oRPC 过程或 DTO 字段：`OncallPing.lastError` 已存在于投递详情 DTO。
- 不改呼叫重试、去重或状态机语义。
- 不在对话框内提供「重新呼叫」动作（另见补投/加急相关需求）。
- 不做错误文本的结构化解析或分类。

## 验收标准

1. 存在 `lastError` 的呼叫行显示可点击错误文本；点击后对话框包含完整错误原文。
2. 对话框提供「复制错误」按钮，复制内容为未截断原文。
3. `lastError` 为空时不渲染触发器，单元格仍显示占位符。
4. 对话框包含 `DialogTitle` 与 `DialogDescription`，触发器有可读的 `aria-label`。
5. 既有 `delivery pings table` 测试全部通过，并新增「展开完整错误」「无错误不渲染入口」两条断言。
6. `vp check`、`vp run -r test`、`vp run -r build` 通过。

## 架构边界

- 纯前端切片：只改 `apps/console/src/features/deliveries/ui`、i18n 消息与对应测试。
- 不触碰 server、infra、oRPC contract 与 SQLite schema。
- 数据仍来自已脱敏的投递详情 DTO，错误文本不额外引入敏感字段。
