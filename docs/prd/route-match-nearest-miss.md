# 事件详情：路由匹配证据按「最接近命中」排序

## 问题

事件详情页的「路由匹配」表把服务端返回的路由按存储顺序逐行列出，命中与未命中混在一起，
未命中的行之间也没有任何优先级。当一条告警没有投递出去时，值班要回答的第一个问题是
「哪条路由本来最该接住它」；现在只能逐行读红色校验徽标，自己数每条路由差几个条件。

路由数量一多（同一套部署里常见十几条），排障时间就花在「找最接近的那条」上，而不是
修配置上。同一产品里已经有「最接近的静默规则排前面」的先例
（`features/deliveries/ui/delivery-suppression-outlook.tsx:55-63`），路由证据却还没有对齐。

## 用户故事

作为值班 SRE，我希望在事件详情的路由匹配表里，命中路由排在最上面，未命中的路由按
「差几个校验」从少到多排列，并把最接近的那条直接标出来，这样我能立刻判断是把哪条
路由的条件写窄了，而不用逐行比对。

## 范围

- 新增纯函数模块 `features/events/model/route-match-explain-order.ts`：
  - `orderRouteMatches`：命中路由保持服务端原顺序排在最前；未命中路由按「未通过校验数」
    升序排列，同分时按路由名、路由 id 稳定排序。
  - `missedCheckCount`：统计 `matched === false` 的校验条数。
  - `closestRouteMiss`：只在**至少两条路由未命中**时返回最接近的一条及其未通过数；
    没有结构化校验的历史快照（`condition` 缺失、`checks` 为空）不参与「最接近」判定，
    避免把「没有证据」读成「差 0 项」。
- 事件详情路由匹配表改用该排序，并在最接近的未命中路由名旁渲染
  `events.detail.routeMatchesClosest` 徽标（中文「最接近：差 N 项」）。
- 中英文案各 1 个键。

## 非目标

- 不改匹配引擎、命中快照、投递写入或 DTO 形状。
- 不新增 URL 筛选、不新增服务端排序参数、不改表头统计口径（仍是「命中数 / 总数」）。
- 不改投递详情里的路由证据面板与抑制规则命中列表。

## 验收标准

1. 命中路由始终排在未命中路由之前，且命中路由之间保持服务端返回顺序。
2. 未命中路由按未通过校验数升序；同分时按路由名、再按路由 id 稳定排序。
3. 只有一条未命中路由时不显示「最接近」徽标（没有可比对象）。
4. 至少两条未命中路由时，徽标只出现在最接近的那条上，数字等于它未通过的校验数。
5. 历史快照（无结构化校验）排在已知失败之后，且不会被标为最接近。
6. 徽标文案为中文 SRE 术语，英文界面同步。

## 架构边界

- 纯前端派生逻辑，放在 `features/events/model/`，不触达服务端、仓储、契约或 SQLite。
- 组件只消费既有 `RouteMatchResult` DTO，无新依赖、无迁移、无新端点，可整体回滚。
