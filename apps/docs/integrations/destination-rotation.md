# 通知目标凭证轮换与故障演练

通知目标凭证包括通用 Webhook Token、Slack Incoming Webhook、邮件网关 Token、飞书机器人 Webhook 与签名密钥，以及飞书应用 `App secret`。轮换不只是把新值粘贴到表单：旧凭据何时失效、尚在队列中的 Delivery、引用同一飞书应用的其他目标，都会影响切换结果。

本页提供可执行的切换顺序和受控故障演练。字段、模板与各类型的成功判定见[通知目标参考](/integrations/destinations)和[通知目标验收与失败判读](/integrations/destination-verification)；投递重试状态见[投递检索、生命周期与重试](/operations/deliveries)。

::: warning 不要把生产值班目标当作试验目标
目标 Test 会立即向真实下游发送消息，并绕过全局暂停、Route、静默和投递队列。先在独立测试接收端、测试群或专用 canary 路由验证；未经验证的凭证和故意失败的请求不要发到生产值班群，正式切换只发送约定好的测试或 canary 消息。
:::

## 先理解四个切换边界

### Test 使用已保存的配置

编辑表单中的 Preview 不会访问下游，只验证模板与合并后的 payload。目标 Test 会重新读取数据库中**已保存**的目标配置；它不接受编辑草稿里的新凭证。因此：

- 只看 Preview 不能证明新 Token、Webhook 或 Header 可用。
- 修改已有目标后，必须先保存，才能 Test 新配置。
- 需要无中断验证时，先创建独立的替代目标，测试通过后再切换 Route。

### 测试成功不等于值班链路成功

Test 不创建 Event 或 Delivery，也不检查 Route 是否命中、目标是否启用、静默是否生效或 Worker 是否正常。计划切换时应同时完成：

1. 目标 Test 验证新凭证、网络、模板与目标接受规则。
2. 一条唯一 canary Event 验证 `Source → Route → Delivery`。
3. 接收端人工确认消息可见，而不是只看页面返回成功。

### Route 切换不会迁移旧队列

Route 的 `destinationIds` 只决定新 Event 创建哪些 Delivery。已经排队的 Delivery 固定引用旧目标：

- 保留旧目标启用，它已有的 `pending` 投递才能继续发送。
- 停用旧目标会暂停它已有的投递；重新启用后会继续，不会自动改发到新目标。
- 删除旧目标会级联删除相关投递历史，不适合作为切换动作。
- 当前版本没有“把一条待发送 Delivery 迁移到另一个目标”的操作。

因此，计划轮换要先让旧队列排空；紧急撤销旧凭证时，则要接受旧队列暂时滞留或最终失败。

### 配置更新会影响后续领取的投递

Worker 领取 `pending` Delivery 时读取当时的目标配置；飞书应用引用的 `App secret` 还会在真正发送前解析。编辑同一个目标会同时影响之后领取的旧队列和新投递。已有 `running` 尝试继续使用领取时的目标配置。

不要在积压很大、告警风暴或集中退避期间原地轮换。先判断旧目标的 `pending` 数量和最早等待时间，再选择“并行目标”或“短窗口原地更新”。

当前版本没有目标级自动 fallback。Route 同时选择多个目标是并行通知，不是失败后改投；每个目标独立成功、重试或失败。

## 选择切换方式

| 方式 | 适用场景 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| 并行替代目标 | 计划轮换 Webhook、Slack、邮件网关或飞书机器人 | 新目标可先测试；旧队列继续排空；回滚边界清楚 | 需要临时多维护一个目标和一次 Route 修改 |
| 原地编辑 | 飞书应用共享凭证必须更新，或下游只允许一个活动端点 | 不修改 Route，操作步骤少 | 没有“保存后、切换前”的缓冲；旧队列会读取新配置 |
| 紧急撤销 | 凭证已泄露、Webhook 已公开或目标被接管 | 最快切断真实外发 | 旧队列无法安全继续；可能需要评估后重新匹配补投 |

不要为了轮换给同一条 Route 同时加入新旧目标，除非本意就是向两个下游各发一份。那会造成重复通知，而不是无缝切换。

## 切换前检查

在变更单中记录以下事实，但不要记录任何明文秘密：

1. 目标名称、类型、发送模式与负责人。
2. 引用该目标的所有启用 Route，以及目标列表中的 Route 覆盖数。
3. 当前 `pending`、`running` 与近 24 小时 `failed` 数量；不要在有大量未知积压时直接改凭证。
4. 模板模式、发送方法与关键运营字段，确认新目标会复制同一份模板。
5. 新凭证的创建时间、计划生效窗口和下游撤销旧凭证的时间。
6. 专用测试接收端、canary Event 编号、核对人和回滚动作。

轮换前先完成一次基线：对旧目标执行 Test，记录成功判定；再发一条唯一 canary Event，记录 Delivery ID。没有基线时，切换后的异常很难区分是新凭证、旧队列还是原本就存在的目标故障。

## 推荐：并行替代目标

适用于通用 Webhook、Slack、邮件网关、飞书机器人，以及可新建飞书应用的计划轮换。

1. **创建新目标。** 保持发送方法、模板、收件人或群范围一致，只替换新凭证或新端点。先保持新目标停用，避免任何误配的 Route 提前发送。
2. **测试新目标。** 停用目标仍可执行 Test。先用内置样例，再用历史 Event 检查真实字段、模板和事件直链。确认接收端收到消息，并核对平台成功条件。
3. **启用新目标。** 此时还没有 Route 引用它；目标是“可发送但不会发送”。
4. **切换 Route。** 逐条把旧目标从 Route 中替换为新目标。不要临时同时保留两者。多条 Route 要核对目标覆盖数和路由列表，避免漏切。
5. **发送真实 canary。** 用唯一标题的 `critical` / `firing` Event 走当前 Route，确认产生新 Delivery，状态为 `succeeded`，接收端可见。飞书应用目标同时检查消息回执；电话演练单独按下方边界执行。
6. **排空旧目标。** 保持旧目标启用，观察其 `pending` 归零。旧目标的队列会继续使用旧配置，因此此时还不能撤销旧凭证。
7. **撤销旧凭证。** 确认旧队列和 `running` 尝试都已结束后，在下游撤销旧 Webhook、Token、签名密钥或网关凭证。
8. **停用旧目标。** 停止其 Route 使用并保留历史。按数据保留和删除影响确认，不要在同一变更窗口直接删除。

如果切换过程中需要回滚，先停止 Route 继续指向新目标，再恢复旧目标及其仍有效的凭证。不要对已经成功的新目标 Delivery 手动重试。

## 按目标类型轮换

| 目标类型 | 推荐方式 | 必须先确认 |
| --- | --- | --- |
| 通用 Webhook | 新目标使用新 Header/Token，测试后替换 Route | 接收端是否允许新旧 Token 并行；接收端按 `eventId` 去重 |
| Slack | 在 Slack 创建新 Incoming Webhook，建立新目标并 Test | 新 Webhook 指向正确频道；响应体去空白后为 `ok` |
| 邮件网关 | 新目标使用新网关 Token，先完成目标 Test 和真实邮件验收 | 网关是否同时接受新旧 Token；`2xx` 只表示网关接受请求 |
| 飞书机器人 | 新建机器人或新签名密钥对应的目标，确认群与机器人范围 | 旧机器人需保留到旧队列排空；Webhook 模式不能电话加急 |
| 飞书应用 | 优先新建应用与目标；无法新建时短窗口更新共享应用记录 | `appRef` 被哪些目标共用；旧应用是否还需处理排队中的卡片 |

### 通用 Webhook 与邮件网关

自定义 Header 的每个值都按潜在凭证保护。编辑已有目标时，Header 名会显示，值不会返回浏览器；提交空白值表示保留原值，输入新值才替换。

如果接收端支持双 Token，先让它同时接受新旧值，再测试新目标并切换 Route。若只允许一个 Token，先清空积压或安排维护窗口；不要先把旧 Token 撤销，再发现新请求已经被旧目标的队列领取。

邮件网关的最终送达不由 Tocsin 观测。切换后即使 Delivery 为 `succeeded`，仍要在网关队列、SMTP 日志和测试收件箱确认；退信不会回写为 Tocsin 失败。

### Slack

新 Incoming Webhook 可以继续指向同一个频道。先创建新目标并 Test，确认频道消息和 `ok` 响应；再替换 Route。旧 Webhook 应保留到旧目标队列排空后再撤销，否则旧 `pending` 会在重试中收到失效响应。

Slack 不提供调用方幂等键。旧目标和新目标可能各发一条测试或 canary，这是验收消息，不是去重失败；正式切换后不要重复触发同一事件。

### 飞书机器人

机器人 Webhook 和签名密钥的轮换可以通过新建群机器人或新目标完成。旧机器人需保留到旧队列排空；如果旧签名密钥已经泄露，应优先撤销，不要为了排空旧队列继续保留。

Webhook 模式没有应用消息引用，不能电话加急。涉及自动加急的目标应使用飞书应用发送模式，并按[飞书应用与电话加急](/integrations/feishu-app)单独验收。

### 飞书应用

飞书应用是可复用资源。多个应用发送模式的目标可以引用同一个 `appRef`，因此修改应用记录会同时影响所有引用它的目标；测试应用凭证、测试目标与真实 Delivery 都不能互相替代。

计划轮换的优先顺序：

1. 新建一个飞书自建应用，完成权限、机器人和群关系配置。
2. 在「飞书应用」登记新 `App ID` 与 `App secret`，执行应用凭证测试。
3. 创建新的飞书应用模式目标，使用相同群 `chat_id`、模板和加急配置，执行目标 Test。
4. 切换所有引用旧应用的 Route，发送真实 canary，确认 `data.message_id` 被记录。
5. 旧目标队列排空后停用旧目标。确认不再需要旧目标历史后，把仍引用旧应用的目标改到新应用或删除旧目标，再删除旧应用记录；不能只靠停用来解除引用。

如果必须在同一个飞书应用上重置 `App secret`：

1. 选定低流量窗口，确认所有引用目标的积压与电话状态。
2. 在飞书侧重置 secret，立即在 Tocsin 编辑应用并提交新 secret。编辑时 secret 留空表示保留旧值，不能把留空当成清除。
3. 执行应用凭证测试。它只验证能否换取 `tenant_access_token`，不会发消息。
4. 对每个受影响的应用发送目标执行 Test，确认群、机器人和权限。
5. 走一次真实 canary，确认消息回执和加急状态。手机演练只使用明确允许的测试接收人。

电话加急是独立链路。全局暂停出站投递不会暂停已经排队的加急记录；轮换期间如果担心旧目标继续拨号，应先停用对应目标并确认已排队 ping 的状态，而不是只切换卡片凭证。

## 原地编辑的限制

编辑已有目标时，以下字段受保留语义影响：

- Slack、飞书机器人和通用 Webhook 的地址：输入新值替换，留空表示保留。
- 飞书签名密钥：输入新值替换，留空表示保留。
- Header 值：表单只显示名称；留空值表示保留，输入新值才替换。
- 飞书应用 `App secret`：编辑应用时留空表示保留。

留空不会让旧 secret 自动失效。如果旧值已经泄露，应在目标平台撤销或重置旧值，再为 Tocsin 提供新值；若当前目标无法安全更新，创建替代目标并切换 Route。

原地编辑后，立即执行已保存目标的 Test。不要只停留在 Preview；Preview 不会发起网络请求，也不会检验 Header、Token 或应用凭证。

## 紧急撤销与重新通知

凭证泄露时，优先阻断，不要等待旧队列排空。

1. **停用受影响目标。** 这会阻止现有队列继续被 Worker 领取，但新 Event 仍可能因为 Route 引用而产生 `pending`。
2. **从 Route 移除受影响目标，或暂时停用相关 Route。** 避免继续累积新投递。若 Route 只有这一个目标，先准备替代目标再切换，或在故障窗口内停用 Route。
3. **撤销旧凭证。** 在 Slack、飞书、邮件网关或自建接收端立即撤销/重置旧值，不要为旧队列继续保留已泄露的凭证。
4. **创建并测试替代目标。** 使用新的独立凭证和已知安全的测试接收端；不要在旧目标上反复 Test 已撤销的 secret。
5. **切换 Route 并发送 canary。** 记录新的 Delivery ID、目标回执和人工确认。
6. **处理旧队列。** 旧目标的 `pending`/`failed` 不会被自动迁移。先判断事件是否仍有效；确认需要补发时，在 Event 详情使用「重新匹配」按当前 Route 生成新投递，不要对已经不确定是否送达的旧 Delivery 盲目重试。
7. **保留证据。** 旧目标暂时停用，记录事件、Delivery、尝试和脱敏错误；按团队保留策略评审后再删除。

如果泄露的是共享飞书应用凭证，停用所有引用该应用的目标，重置应用 secret 或迁移到新应用，再逐个执行应用凭证测试、目标 Test、真实 canary 和加急边界确认。

## 目标侧故障演练

演练的目的是验证“操作者能否识别并正确处置”，不是在生产目标上制造故障。先建立专用演练目标：

- 通用 Webhook 使用可控制状态码和延迟的自建接收端。
- Slack、邮件和飞书使用测试频道、测试收件人或测试网关；不要向生产值班对象发送故意错误的请求。
- 全链路演练使用 canary Source 与 Route，记录唯一标题和 Event/Delivery ID。

### 演练矩阵

| 演练场景 | 配置方式 | 预期观察 | 不应做什么 |
| --- | --- | --- | --- |
| 凭证无效 | 在演练目标填入错误 Token，执行 Test | `401`/`403` 或目标拒绝；修正后 Test 成功 | 在生产目标上反复试错 |
| 永久协议错误 | 让演练接收端返回 `400`、`404` 或 `422` | Delivery 失败且不应自动重试；错误文本已脱敏 | 用大量真实告警压测 |
| 限流或暂时故障 | 让接收端返回 `429` 或 `5xx` | Delivery 进入退避重试；保留尝试记录 | 在退避期间手工连点重试 |
| 超时 | 让接收端延迟超过 `TOCSIN_DESTINATION_TIMEOUT_MS` | 记录超时并按可重试错误处理；目标可能已经收到请求 | 把超时当成“肯定未送达” |
| Slack 业务拒绝 | 使用测试 Slack 目标制造无效 blocks 或撤销测试 Webhook | HTTP 与 `ok` 判定分开，目标拒绝不会按普通网络错误处理 | 直接改生产频道 |
| 飞书业务拒绝 | 使用测试应用/群制造权限或群关系错误 | 页面保留飞书业务码与修复提示；只有白名单错误重试 | 把每次 2xx 都当作已送达 |
| 电话失败 | 仅用明确允许的测试接收人验证权限或额度错误 | 加急记录独立显示 `failed` 或等待重试 | 让生产值班手机承受演练 |

通用 Webhook 的 `408`、`409`、`425`、`429`、`5xx`、连接失败和超时会进入自动重试；其他 `4xx` 通常不会。Slack 必须同时满足 HTTP `2xx` 与响应体 `ok`；飞书应用要求业务成功码，电话加急还要求可引用的消息 ID。各类型的完整规则见[通知目标验收与失败判读](/integrations/destination-verification)。

### 演练步骤

1. 先完成成功基线：Test 成功，再走一条唯一 canary Event。
2. 只改变一个变量，例如 Token、响应状态或延迟；同时修改多个字段会让根因无法判断。
3. 对自动重试场景，让演练接收端在第一次失败后恢复成功，观察同一 Delivery 的尝试次数、下次重试时间和最终状态。
4. 每次失败后恢复配置，再执行 Test 和新的唯一 canary。不要用旧 Delivery 结果证明新凭证可用。
5. 核对目标端实际收到几条消息，记录“至少一次”语义造成的可能重复。
6. 结束后关闭演练目标或移除演练 Route，避免其进入生产值班链路；确认没有遗留静默规则或全局暂停。

演练记录只保留目标名称、时间、脱敏错误、HTTP 状态、业务码、Delivery ID、尝试次数和操作者。不要在工单、聊天或截图中写入完整 Webhook URL、Header 值、Token、签名密钥或飞书 `App secret`。

## 完成标准

一次轮换只有同时满足以下条件才算完成：

- 新目标 Test 成功，接收端人工确认收到。
- 当前 Route 的真实 canary Delivery 为 `succeeded`，目标回执和页面一致。
- 旧目标没有未处理的 `pending`/`running` 投递，或已明确记录放弃与补投决策。
- 旧凭证已在下游撤销，旧目标已停用或按保留策略隔离。
- 飞书应用涉及的每个目标、电话接收范围和去重行为已核对。
- 无遗留全局暂停、临时静默或演练 Route；变更记录不含秘密。
