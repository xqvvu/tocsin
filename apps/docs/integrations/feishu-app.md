# 飞书应用与电话加急

飞书通知目标有两种发送方式：

| 发送方式 | 凭证与目标 | 能发送 | 能电话加急 |
| --- | --- | --- | --- |
| Webhook 机器人 | 群机器人 `webhookUrl`，可选签名密钥 | 文本或卡片 | 否。Webhook 响应没有可引用的应用消息 |
| 飞书应用 | 已登记的应用、群 `chat_id` | 由应用向群发送文本或卡片 | 是。应用发送成功后返回消息引用 |

只有**应用发送模式**能发起 `urgent_phone`。Webhook 消息不是应用自己发送的，没有 `message_id`，因此不能加急。普通消息与电话加急是两条独立链路：卡片发送失败只影响 Delivery，电话失败只影响对应的加急记录，不会互相重试。

```text
Route → 飞书应用模式的目标 → 应用向群发送卡片并取得 message_id
                                      ↓
                        成功的 firing Delivery
                           ├─ 自动：严重程度命中门槛
                           └─ 手动：操作者在投递详情发起
                                      ↓
                      每位呼叫对象一条 ping → 加急 Worker → 电话呼叫
```

电话语音内容是飞书固定的“给你发了一条加急消息”提示，不包含告警标题或正文。值班上下文仍在应用发送到群里的那张卡片中。

## 上线前提

当前适配器固定调用飞书开放平台 `open.feishu.cn`，不调用 Lark 国际版域名。使用前先在飞书开发者后台准备一个自建应用，并逐项核实：

| 前提 | 为什么需要 |
| --- | --- |
| 已取得应用的 `App ID` 与 `App secret` | 用于换取 `tenant_access_token`，发送应用消息和执行加急 |
| 已启用机器人能力 | 未启用时飞书返回 `230006` |
| 应用机器人已加入目标群 | Tocsin 通过群 `chat_id` 发送；机器人不在群内返回 `230002` |
| 群允许该机器人发起加急 | 群可设为所有成员可加急，或仅群主/管理员可加急且机器人是管理员；否则返回 `230052` |
| 呼叫对象在应用可用范围内且仍在群内 | 用户不在可见范围、已离职或 ID 类型不匹配时会拒绝或出现在无效用户列表中 |
| 企业仍有电话加急额度 | 电话与短信加急是飞书侧计费、限额能力；额度耗尽返回 `230024` |

所需权限：

| 能力 | 权限 |
| --- | --- |
| 应用发送消息 | `im:message` 或 `im:message:send_as_bot` |
| 电话加急 | `im:message.urgent:phone`；历史版本接口可能使用 `im:message.urgent:phone_send` |
| 以 `user_id` 指定呼叫对象 | 额外需要 `contact:user.employee_id:readonly` |

权限变更后要发布应用版本才会生效。生产配置推荐使用 `open_id`，减少对员工 ID 和额外通讯录权限的依赖。

## 登记飞书应用

1. 在飞书开发者后台创建或选择自建应用，完成机器人能力、权限、可用范围和版本发布。
2. 把应用机器人加入计划接收告警的群，并确认群的加急权限允许该机器人操作。
3. 在 Tocsin 打开「飞书应用」页面，选择「新增」。
4. 填写可辨认的名称、`App ID` 与 `App secret`，保存。
5. 在应用行执行凭证测试。成功提示表示 `App ID` 与 `App secret` 能换取 `tenant_access_token`。

::: warning 凭证测试不是完整验收
「飞书应用」页的测试只验证应用凭证能否换取 token。它不会发送消息，也不会检查机器人是否在目标群、群加急设置、接收人范围或加急额度。完成凭证测试后，还必须测试通知目标并走通一次真实 Delivery。
:::

应用是可复用资源，一个应用可以被多个飞书通知目标引用。目标只保存 `appRef`；发送或加急时，服务端才解析应用凭证并换取 token。编辑应用时 `App secret` 留空表示保留原值。

被应用发送模式的飞书目标引用时，应用不能删除；先在目标中改用其他应用，再回到「飞书应用」删除。应用列表的「被引用」列会列出引用它的目标。

## 配置应用发送目标

在「通知目标」新建或编辑一个飞书目标：

1. 将「发送方式」设为「飞书应用」。
2. 选择一个已登记的「飞书应用」。
3. 填写目标群的 `chat_id`。群 `chat_id` 通常形如 `oc_xxxxxxxxxxxx`，必须对应机器人已加入的群。
4. 按需修改模板。内置卡片、普通文本和飞书 Card JSON 都可用于应用发送。
5. 保存后执行「测试」。测试会绕过投递队列，真实向群发送一条消息，但不会创建 Event 或 Delivery。

如果只希望通过应用发送卡片，不启用电话加急，可以保持「电话加急」区块为空。应用发送模式本身不要求配置呼叫对象。

## 配置电话加急

在同一个飞书目标的「电话加急」区块中配置：

| 配置 | 行为 |
| --- | --- |
| 自动加急 | 开启后，满足全部自动条件的成功 Delivery 会创建呼叫；关闭后仍需保留呼叫对象，供操作者在投递详情手动发起 |
| 严重程度门槛 | 只有这些规范化严重程度会触发自动呼叫；不选择时按 `critical` 处理 |
| 用户 ID 类型 | `open_id`、`user_id` 或 `union_id`，必须与呼叫对象值的实际类型一致 |
| 呼叫对象 | 每行一个用户 ID，最多 200 个且不能重复；v1 一个呼叫对象产生一条 ping |

自动加急必须同时满足以下条件：

1. 投递目标是飞书应用发送模式。
2. Delivery 已成功，且目标返回了可引用的飞书消息。
3. 自动加急已开启，并且至少配置了一个呼叫对象。
4. Event 的规范化状态是 `firing`；`resolved` 和 `unknown` 不会自动呼叫。
5. Event 的严重程度在自动加急门槛内。

自动加急在写入投递成功状态之前发起：电话不可撤销，不能依赖本地写库是否成功。因此成功状态未能写入时，投递可能显示失败而电话已经拨出；遇到这种情况先向接收人核实，不要直接补呼。

手动加急从 Delivery 详情的「电话加急」区域发起。它要求该 Delivery 带有飞书消息引用、目标已启用，且当前目标仍配置了呼叫对象。手动入口不受「自动加急」开关或严重程度门槛限制，但会确认本次将呼叫多少人；该动作不可撤销。

::: danger 先确认接收对象
电话加急会立即打扰真实值班人员，并消耗企业额度。首次配置应使用测试群或明确允许演练的小范围接收人，不要直接把生产告警路由切到未经验证的呼叫列表。
:::

## 去重与重试

同一告警、目标和呼叫对象在 5 分钟去重窗口内不会重复产生 ping。自动路径还会锁定“同一 Delivery + 呼叫对象”：即使卡片重试后得到新的消息引用，也不会再次自动拨打同一人。

手动加急复用 5 分钟窗口；窗口过后，操作者可以对同一个已经成功投递并已自动呼叫过的 Delivery 再发起一次显式补呼。请求返回成功只表示 ping 已入队或立即派发已尝试，最终是否拨出以投递详情的「电话加急」表为准。

每个 ping 默认最多尝试 3 次，退避从 30 秒开始按 2 倍增长，单次上限 15 分钟。以下情况通常可自动重试：

- 网络错误、超时和 HTTP `429`。
- 飞书限流业务码 `99991400`，以及发送链路的 `11232`、`11233`。
- 呼叫对象未读加急过多，飞书返回 `230023`。
- 缓存的 tenant token 失效时，适配器会丢弃缓存并换取新 token 再试一次。

权限、群配置、接收人范围、额度耗尽和未知业务码通常不可重试。修复问题后，可回到该 Delivery 再发起手动加急；若仍在 5 分钟窗口内，去重会拒绝同一呼叫对象。

全局「暂停出站投递」只暂停卡片 Delivery，不暂停独立的加急队列。被静默规则抑制的 Delivery 不会发送卡片，也不会产生新的电话 ping；已经发出的电话无法撤回。相关语义见[投递生命周期与重试](/operations/deliveries)与[告警静默与维护时段](/operations/suppressions)。

## 读取加急记录

Delivery 详情的「电话加急」表按呼叫对象逐行显示：

| 字段 | 含义 |
| --- | --- |
| 状态 | `scheduled` 等待、`running` 已领取、`fired` 已呼叫、`failed` 终态失败 |
| 触发方式 | 自动，或手动及发起操作的用户 ID |
| 尝试次数 | 已领取的呼叫尝试数，以及该 ping 的最大次数 |
| 创建时间 / 呼叫时间 | 入队时间与飞书接受呼叫的时间，两者可能不同 |
| 下次重试 | 等待退避或重新入队的计划时间；终态时为空 |
| 最近错误 | 已脱敏的错误原因；可打开详情对话框查看与复制完整文本 |

如果页面显示“为什么没有自动加急”，该提示依据**通知目标当前配置**给出第一个未满足的条件。历史投递可能在目标配置修改后得到不同解释；已有 ping 记录才是实际执行证据。

`running` 只表示某个 Worker 已领取尝试。进程在拨号前后中断时，超时回收会区分“尚未开始呼叫”和“可能已经拨出”：前者在仍有预算时自动重试，后者转为失败并在错误中说明“可能已拨出、未自动重试”。此时先向接收人核实，再决定是否手动补呼，避免重复电话。

## 常见错误

| 错误码或现象 | 常见原因 | 处理 |
| --- | --- | --- |
| `10003` / `10014` | App ID、App secret 或应用状态无效 | 回到飞书开发者后台核对凭证与应用状态，然后重新测试 |
| `230006` | 应用未启用机器人能力 | 开启机器人能力，发布版本后重试 |
| `230002` | 机器人不在目标群 | 把应用机器人加入 `chat_id` 对应的群 |
| `99991672` | 缺少发送或加急权限 | 申请对应权限并发布应用版本 |
| `230052` | 群不允许该机器人加急 | 调整群加急权限，或让机器人成为群管理员 |
| `230013` / `11236` / `230001` | 接收人不在可用范围、已离职、ID 类型错误或全部无效 | 核对 `open_id` / `user_id` / `union_id`、应用范围与群成员关系 |
| `230024` | 企业电话加急额度耗尽 | 由飞书管理员检查额度与计费；Tocsin 不会无限重试 |
| `230023` | 接收人的未读加急过多 | 提醒接收人阅读飞书加急消息；队列会退避重试 |
| `230012` / `230098` / `230110` | 消息不是当前应用发送、属于折叠消息或已删除 | 确认目标仍引用发送该卡片的同一应用；必要时重新投递并产生新消息 |
| `230025` | 卡片超过飞书消息大小限制 | 精简卡片模板后重新测试 |
| `99991400` / HTTP `429` | 应用级限流 | 保留自动退避，避免告警风暴和批量调试同时拨号 |
| 有成功 Delivery，但没有 ping | 自动关闭、非 `firing`、级别不命中、没有呼叫对象、Webhook 模式、无消息引用或去重 | 先读「为什么没有自动加急」，再核对当前目标配置与投递时间 |

应用凭证、`App secret`、tenant access token 与完整请求头都不得写入工单、文档或浏览器存储。呼叫对象 ID 是值班排障所需的运维标识，可以出现在已认证 dashboard 与投递证据中。

可移植配置导出会把飞书应用密钥替换成环境变量引用，不输出明文 secret；数据库备份仍包含应用凭证，必须按 secret 材料保护。格式见[可移植配置参考](/operations/portable-config#飞书应用)，备份要求见[备份、恢复与升级](/operations/backup-restore)。

## 上线验收

1. 在「飞书应用」完成凭证测试。
2. 在应用发送模式的目标中执行「测试」，确认目标群收到真实卡片。
3. 用一条非生产 `critical`、`firing` 告警走完 Route → Delivery，确认卡片成功且只呼叫预期对象。
4. 在 5 分钟内重发相同告警，确认没有重复电话；再验证 `resolved` 或低于门槛的级别不会自动呼叫。
5. 在投递详情手动发起一次小范围加急，确认操作者、呼叫时间和状态被记录。
6. 检查 `tocsin.delivery`、`tocsin.oncall` 与 `tocsin.worker.oncall` 日志，确认失败原因已脱敏且与页面一致。
7. 把应用凭证、飞书额度负责人和人工补呼流程写入值班手册。

日志类别与安全取日志方式见[日志与可观测性](/operations/observability)；认证或 Webhook 问题见[故障排查](/operations/troubleshooting)。
