# 告警静默与维护时段

告警静默用于在一段明确时间内暂停符合条件的通知。它适合计划发布、数据库迁移、演练，以及已经定位但暂时无法消除的重复告警。

不要用停用整个告警源、路由或通知目标来代替窄范围静默。那样会同时影响无关告警，而且不易回答“当时为什么没有通知”。风暴期间如何按影响面选择静默、停用或全局暂停，见[告警风暴与大面积误报的处置顺序](/operations/incident-playbook)。

## 先理解影响层级

```text
Webhook → Event（始终保留）→ Route 匹配
                              → 每条 Delivery 按静默规则判定
                                  ├─ 命中：状态 suppressed，不发送
                                  └─ 未命中：进入正常 Worker 投递
```

| 对象 | 静默时会发生什么 |
| --- | --- |
| Event | 照常保存，规范化字段和路由匹配证据仍可检查。 |
| Delivery | 创建时命中规则的记录直接成为终态 `suppressed`，不会产生发送尝试；若在重试退避期间转为静默，已有失败尝试保留，但不会新增发送。 |
| 自动电话提醒 | 不发起。被抑制的 Delivery 没有消息回执，因此详情页也不能手动加急；机制见[飞书应用与电话加急](/integrations/feishu-app#去重与重试)。 |
| 已发出的电话 | 不会被撤回或取消。静默只阻止尚未发送的通知。 |
| 窗口结束后的新事件 | 按正常链路投递；窗口内被静默的记录不会自动补发。 |

::: danger 值班安全边界
静默会同时压住普通消息和自动电话提醒。创建前必须核对「命中范围」和「自动电话提醒」影响面板。被静默的告警无法通过 Tocsin 手动加急，不要把它当作“只停群消息、电话仍会响”的开关。
:::

## 创建一条规则

在 dashboard 打开「告警静默」，选择「创建静默规则」，然后按顺序填写：

1. **用途**：选择「临时静默」或「维护时段」。两者使用同一套匹配和生效机制，只表达不同运维意图。
2. **规则名称和原因**：名称会进入投递的审计快照；原因建议填写变更单或事件编号，例如 `CHG-1234`。
3. **开始与结束时间**：结束时间必填，且必须晚于开始时间。时间按控制台时区解释，页面会显示当前使用的时区。
4. **匹配条件**：选择告警源、通知目标、严重级别、告警状态，或填写指纹、标签、标题包含、内容包含。
5. **核对影响范围**：检查规则会命中哪些告警源、级别和状态，以及有多少个启用自动电话提醒的目标在范围内。
6. **启用规则**：保持启用并保存。开始时间未到时状态为「待开始」，到达开始时间后自动进入「生效中」。

未填写的条件维度表示“不限制该维度”。例如只选择一个告警源，规则仍会匹配该源下所有严重级别、状态和通知目标。所有已填写维度必须同时满足；告警源、通知目标、严重程度和状态的多选中任一值可以命中，多条标签、多个标题片段或内容片段则必须全部满足。

::: warning 无条件的全量静默
如果所有条件都为空，规则会在时间窗内静默全部告警。保存时必须再次确认；生效后 dashboard 顶部会显示「全量静默生效中」。
:::

## 常用范围

从具体对象发起静默可以减少手填范围错误：

| 入口 | 预填范围 | 适合场景 |
| --- | --- | --- |
| 事件详情 →「静默此指纹」 | 当前告警源与精确 fingerprint | 只暂停一个重复告警。 |
| 事件标签 →「静默此标签」 | 当前告警源与一个 `equals` 标签 | 暂停某服务、环境或实例组的已知噪声。 |
| 路由行 →「临时静默此路由」 | 当前路由条件与其通知目标 | 计划变更期间暂停一条已知投递路径。 |
| 通知目标行 →「临时静默此目标」 | 当前通知目标 | 某个渠道维护或故障期间的短时收口。 |

这些操作创建的是独立 Suppression，不会修改原路由或通知目标，也不会随之后的 Route 编辑自动变化。保存前仍要检查预填条件和影响面板。

### 匹配细节

- 告警源、通知目标、严重级别、状态和 fingerprint 采用任一所选值命中。
- 标签的「等于」区分大小写；标签的「包含」是区分大小写的子串匹配。
- 标题包含和内容包含不区分大小写；填写多个片段时，每个片段都必须出现。
- fingerprint 是精确匹配，不支持 glob 或正则表达式。
- 严重级别和状态匹配规范化后的值，例如 `critical`、`firing`、`resolved`。

## 生效、修改与结束

| 状态 | 含义 |
| --- | --- |
| 待开始 | 已启用，但当前时间早于开始时间。 |
| 生效中 | 当前时间位于 `[开始时间, 结束时间)`，命中规则的投递会被静默。 |
| 已结束 | 已过结束时间，不再静默；无需人工关闭。 |
| 已关闭 | 运维显式停用，优先级高于时间状态。 |

尚未开始发送的在队投递会在 Worker 认领时再次检查当前规则。因此，规则在重试退避期间变为生效，也能阻止下一次发送；已经成功的投递不会被追溯改写。

提前结束维护时，优先在列表中使用「关闭」而不是删除。关闭立即停止后续匹配，并保留规则、命中记录和投递关联。删除也会停止规则，但被抑制 Delivery 上的原因快照仍会保留，只不再关联原规则。

::: tip 窗口结束不会发摘要
Tocsin 不会在结束时主动通知“本窗口静默了多少条”。需要复盘时，应在管理窗口期间或结束后打开规则详情，查看「已静默通知」并核对时间范围。
:::

## 核对与审计

值班期间可以从四处确认静默是否生效：

1. dashboard 顶部：显示「生效中的静默：N 条」；存在全量静默时显示红色「全量静默生效中」。
2. 静默列表：生效中的规则排在最前，最快到期的规则优先显示。
3. 规则详情：查看时间窗、原因、匹配条件，以及该规则命中的 Delivery。
4. Event / Delivery：Event 仍可打开；`suppressed` Delivery 显示原因快照、抑制时间和通知目标。创建时即被静默的 Delivery 尝试次数为 0；重试中途被静默的记录保留已发生的尝试，但不再发送。

判断“没有通知”时，不要只看消息群。先确认顶部是否有生效静默，再检查 Event 是否到达；若 Event 存在但没有正常 Delivery，继续按[故障排查](/operations/troubleshooting)检查路由和通知目标。

## 紧急恢复

当确认某条规则范围过大或误伤关键告警时：

1. 从顶部静默提示进入「告警静默」。
2. 找到「生效中」的规则，先检查其匹配条件与命中记录。
3. 使用「关闭」立即停止规则，并在确认框中核对规则名称。
4. 确认顶部提示消失或数量减少。
5. 从上游发送一条测试告警，确认 Event 创建后产生新的正常 Delivery。

关闭或到期只影响后续判定。旧的 `suppressed` Delivery 仍保持终态且不能手动重试，不能用它们证明通知已经恢复。已呼叫的电话也不会因关闭规则而撤回。

## 排障清单

| 现象 | 检查 |
| --- | --- |
| 顶部显示全量静默 | 检查条件完全为空的规则；立即关闭误建规则。 |
| 规则显示生效中但未命中预期告警 | 对比 Event 的规范化值；检查标签大小写、fingerprint、严重级别和状态。 |
| 规则引用的告警源显示已停用或已删除 | 更新规则范围。已删除的源使用 ID 显示，不会自动放宽成其他源。 |
| 规则引用的通知目标不存在 | 编辑规则重新选择目标；范围预览会提示当前没有启用目标。 |
| 静默结束后仍有旧记录为 `suppressed` | 这是不可追溯改写的终态；用新 Event 验证后续投递。 |
| 找不到规则命中记录 | 规则只记录实际命中的 Delivery；确认 Event 已到达且路由、目标当时均有效。 |
