# 值班交接与通知链路验收

值班交接不是“看一眼 dashboard 都是绿色”。上一个班次可能留下了全局暂停、临时静默、停用的目标，或者一批正在退避的失败投递；这些状态都会让页面看起来很安静。交接要回答三个问题：

1. 有没有正在压住告警的开关？
2. 有没有正在失败、积压或等待人工决定的投递？
3. 通知链路现在真的能到人吗？

本页覆盖日常班次交接。事故进行中的止噪顺序见[告警风暴与大面积误报的处置顺序](/operations/incident-playbook)，投递状态与重试细节见[投递检索、生命周期与重试](/operations/deliveries)。

::: warning 不要把“安静”当成“正常”
全局暂停、生效中的静默和停用的通知目标都能让通知停止，但 Event 仍会照常接入。交接时必须逐项确认这些开关，而不是只看有没有新消息。
:::

## 交接前：交班人固定状态快照

交接记录应以 dashboard 当前状态为准，不凭记忆。至少覆盖下表；数字和对象名称要写进交接记录，不要只写“正常”。

| 位置 | 记录什么 | 为什么重要 |
| --- | --- | --- |
| 设置 → UI → 投递急停 | 是否暂停、暂停开始时间与操作者；恢复后查看“最近一次暂停”区间 | 暂停期间新投递只入队不发送，最容易造成“看起来没告警” |
| dashboard 顶部与「告警静默」列表 | “生效中”和“待开始”的规则数量、名称、结束时间、作用范围；是否有“全量静默生效中” | 静默会自动到期，但也会误伤关键告警；交接要明确谁在等它结束 |
| 告警源列表 | 已停用的告警源 | 停用源会在凭据校验前拒绝新 Webhook，不创建 Event |
| 路由列表 | 已停用的路由、被停用的目标数量、告警源可达性提示 | 停用路由不会为新 Event 创建投递；已有投递仍按目标与队列状态处理 |
| 通知目标列表 | 已停用的目标、最近成功/失败时间、排队数量、近 24 小时失败数 | 一眼看出哪个渠道在失败或积压 |
| 投递列表 | `pending` 数量与最早等待时间；近 24 小时 `failed` 数量；是否存在“目标已受理但记录失败”的记录 | 积压和最终失败是交接的核心风险 |
| 飞书投递详情 | 最近失败或状态未知的电话加急记录、接收人和错误 | 电话没有全局列表，只能从相关投递详情核对 |
| 设置 → 后台工作进程 | 投递与加急 Worker 是否为“未启动”或“失败” | 这是当前进程快照，重启后会清空，不能当作历史 |
| 设置 → 数据库存储、宿主机与备份系统 | 数据库体积、数据卷余量、最近一次成功备份 | 容量和备份问题通常跨班次才暴露 |
| 变更记录 | 本班次做过的升级、配置导入、Token 轮换、目标或路由修改 | 接班人需要知道哪些变化尚未验证 |

::: danger 交接记录不写秘密
交接记录、群消息和工单里不要出现 Source Token、目标签名密钥、密码、飞书应用 secret 或完整 `Authorization` 头。只写资源名称、ID、变更单号和操作者。
:::

### 交接记录模板

把下面这段填完再交班；没有内容的项写“无”，不要省略。

```text
班次 / 交班人 / 接班人 / 时间：
实例版本 / 最近一次变更：
投递暂停：是/否；开始时间与操作者；最近一次暂停区间
生效中静默：N 条（名称 / 结束时间 / 范围）；待开始：N 条
停用对象：告警源 …；路由 …；通知目标 …
投递：pending N 条，最早等待 …；近 24h failed N 条（目标 / 错误 / 负责人）
电话：近 24h 失败或状态未知的 ping …；待核实 …
Worker：投递 …；加急 …；/api/ready 结果 …
容量 / 备份 / 证书：…
未完成动作与负责人：…
下一次 canary 与巡检时间：…
```

## 交接时：验收通知链路

状态快照只能证明“配置是什么”，不能证明“消息现在能到”。交接时至少完成一层验收；关键班次或刚改过配置时完成两层。

### 第一层：目标测试

在「通知目标」对每个值班目标执行「测试」：

- 测试会立即通过当前配置发送一条真实消息，默认使用内置样例，也可以选择历史 Event 验证真实模板字段。
- 测试绕过投递队列、全局暂停、路由和静默，不创建 Event 或 Delivery。因此它只能证明目标凭证、网络和模板可用，不能证明“Webhook → 路由 → 投递”链路通。
- 停用的目标仍然可以测试发送；测试成功不代表路由会继续使用它。
- 确认接收端真的看到了消息，而不只是页面显示“已接受”。同时核对平台返回的业务结果：飞书看业务码，Slack 看响应体是否为 `ok`，并确认消息引用已记录。

### 第二层：全链路 canary

用专用 canary 告警源发送一条唯一标题的测试告警，走完整链路：

1. 确认 canary 路由只指向监控团队控制的测试频道或测试 Webhook，不要命中生产值班目标或电话加急。
2. 通过 canary 告警源的 Webhook 发送一条 `critical` / `firing` 的测试载荷，标题带时间戳或唯一标记。
3. 确认接口返回 `202`，并在「事件」中找到对应 Event 及其路由匹配证据。
4. 打开关联 Delivery，确认状态为 `succeeded`，并检查回执。
5. 确认接收端在约定窗口内收到消息；没收到时按[故障排查](/operations/troubleshooting)处理，不要只看 dashboard。

执行前先确认没有全局暂停或覆盖 canary 的静默：暂停期间投递只会入队，静默会让投递直接成为 `suppressed`。这两种情况都不是链路故障，但也不能证明链路通。canary 的频率、容量和外部调度见[生产监控与告警基线](/operations/monitoring#用-canary-覆盖完整链路)。

### 第三层：电话加急

电话会打扰真实值班人员，交接时默认只核对配置和最近记录，不做未协调的拨号。

- 需要现场验证时，先用测试群或明确允许演练的小范围接收人，并提前告知对方。
- 手动加急只对带飞书消息引用的 App 模式投递可用，且要求目标已启用、仍配置了呼叫对象；入口在 Delivery 详情。
- 同一告警、目标和呼叫对象在 5 分钟内不会重复拨号；窗口内的手动补呼会被拒绝。
- 全局“暂停出站投递”不暂停独立的加急队列；已经排队的 ping 仍可能拨出。暂停只阻止新的卡片投递，依赖卡片成功的自动加急也就不会产生。
- 最近 24 小时的失败或状态未知记录，从相关飞书投递详情的「电话加急」表核对。没有全局加急列表。

电话加急的完整门槛、去重和错误码见[飞书应用与电话加急](/integrations/feishu-app#去重与重试)。

### 顺带确认通知直链

在「设置 → 运行时与生效参数」检查“通知直链基址”。如果为空或仍是 `localhost`，收件人打不开消息里的事件链接；修正 `SERVER_URL` 后重建容器，再发送测试消息确认链接可打开。字段说明见[设置与运行态操作](/operations/settings#运行时与生效参数)。

## 接班后 30 分钟

不要只信交接记录，抽样复核三项事实：

1. **开关**：顶部静默提示与「设置 → UI」的暂停状态是否与记录一致；不一致时先按当前状态处理，再联系交班人。
2. **积压**：投递列表的 `pending` 数量与最早等待时间是否在下降；持续上升时查 Worker、目标启用状态和暂停开关。
3. **失败**：近 24 小时 `failed` 是否都有负责人和下一步；不要对“目标已受理但记录失败”的投递重试。

然后确认：

- `/api/ready` 返回 `200` 且 `status: "ok"`，Worker 不是“未启动”或“失败”。
- 待开始的静默和维护窗口有明确的结束时间与负责人；不需要的规则及时“关闭”，不要删除。
- 当天计划的升级、Token 轮换或配置导入已经完成验证，或明确不在本班执行。
- canary 下一次执行时间已知，接收端有人负责确认。

## 常见误区

| 现象 | 实际边界 |
| --- | --- |
| 全局暂停期间测试目标仍收到消息 | 测试绕过队列与暂停，是真实发送，不代表投递链路正常 |
| 停用目标后测试仍成功 | 测试不检查启用状态；路由不会因此恢复使用该目标 |
| 恢复投递后立刻出现一批通知 | 暂停期间积压被保留，恢复后会补发；先评估积压和电话影响 |
| Worker 显示“空闲”就说明没有积压 | 空闲只说明当前没有执行批次；积压看 `pending` 数量和最早等待时间 |
| 静默结束后没有补发窗口内的通知 | 静默是跳过，不是排队；窗口内被抑制的投递不会自动补发 |
| 交接时把失效规则删除更干净 | 删除会丢失规则与命中记录的关联；优先“关闭”并保留证据 |
| 电话加急没有全局列表就代表没有失败 | 记录在各自 Delivery 详情；按飞书目标和失败投递逐条核对 |
| 刚升级完只看 `/api/health` 就交班 | `/api/health` 只证明进程能响应；用 `/api/ready` 和真实 canary 验证完整链路 |
