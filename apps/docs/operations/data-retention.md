# 数据保留与 SQLite 容量

Tocsin 把敏感调试数据与业务审计记录分开处理。「原始载荷保留天数」只清理 Event 的原始载荷和请求头，不会删除 Event、Delivery、投递尝试或加急记录。容量规划必须同时考虑原始数据保留期和持续增长的历史表。

事件中的原始调试字段、清理后的展示和证据导出见[事件检索与证据](/guide/events#原始调试与保留策略)；数据库备份与恢复见[备份与恢复](/operations/backup-restore)。

::: warning 两种「保留」不要混淆
设置里的保留天数不是 Event/Delivery history retention。到期后仍会保留规范化事件、路由匹配快照和投递结果，因此数据库文件通常不会随原始载荷清理而缩小。
:::

## 配置原始载荷保留期

在 dashboard 的「设置」中修改「原始载荷保留天数」：

| 项目 | 当前行为 |
| --- | --- |
| 默认值 | `30` 天 |
| 可设置范围 | `0`–`3650` 的整数 |
| 时间计算 | 每个「天」按 24 小时计算，不按本地日历零点切换 |
| 影响对象 | 所有告警源产生的 Event，包括 Provider 解析失败记录 |
| 存储位置 | SQLite 运行设置，不是环境变量 |

保存后无需重启容器。新值在下一次 Webhook 接入事务中读取并生效；可移植配置中的同名设置也使用这个字段，见[可移植配置参考](/operations/portable-config#基础设置)和[环境变量与运行时配置](/operations/configuration#读取与生效规则)。

### `0` 不是关闭清理

`0` 表示清理边界就是当前 Webhook 的接收时刻。下一次接入会把更早 Event 的原始载荷和请求头清除，而本次新 Event 仍会保存。

例如保留期为 `30` 天时，在 `2026-11-01T12:00:00Z` 接受的 Webhook 会清理接收时间早于 `2026-10-02T12:00:00Z` 的原始数据。该时间边界由接入时间减去 `30 × 24` 小时得到。

### 在详情页查看截止时间

Event 的「原始调试」页签和 Delivery 的「载荷」页签在原始数据尚未清理时，会显示「原始载荷保留至」时间与当前保留策略。截止时间按 Event 的接收时间加当前保留天数计算，并使用 dashboard 配置的时区显示；修改保留天数后，未清理 Event 的提示会按新值重新计算。

超过窗口但尚未被后台清理时，提示会改为“等待后台清理任务处理”。`0` 天或设置读取失败时不显示未来截止时间，但页面仍会正常展示当前可读的原始数据。该提示只说明策略边界，不保证后台会在截止瞬间完成清理。

### 清理何时发生

- 清理没有独立的定时任务，也不会在启动时全库扫描。它由后续 Webhook 接入触发，并在响应请求前按接收时间从旧到新最多清理 100 条过期 Event，再把剩余积压交给进程内后台 sweep。
- 清理是实例级的：任意一个启用的告警源收到 Webhook，都会按同一保留期清理所有告警源的过期原始载荷；保留天数不能按 Source 单独设置。Provider 解析失败的 Webhook 只执行有界清理，不启动后台 sweep。
- 如果没有新的 Webhook，旧载荷可能超过配置窗口后仍暂时可见。需要立即收敛时，发送一条经过认证的测试告警，再核对旧 Event。
- 调大保留期不会恢复已经清理的数据；调小保留期会缩短后续清理边界，但同样要等下一次接入触发。
- 后台 sweep 失败不会让已成功的 Webhook 返回失败。后续 Webhook 会重新尝试清理，因此以 Event 详情中的清理提示为准，不要把单次后台延迟误判为接入失败。

::: danger 清理不可逆
清理只覆盖当前记录，不提供「取消清理」或历史回滚。需要长期复盘的上游字段应先写入规范化字段、下载证据包，或按组织策略延长保留期。
:::

## 清理什么，保留什么

达到保留边界后，Tocsin 会把 Event 的 `rawPayload` 替换为内部清理标记，并把 `rawHeaders` 置空。dashboard 会把这种状态显示为「原始数据已按保留策略清理」，不会把内部标记当作上游发送的 JSON。

| 数据 | 保留期到期后的行为 |
| --- | --- |
| 原始载荷与原始请求头 | 清除；Event 和 Delivery 详情显示已清理提示 |
| 标题、消息、严重程度、状态、fingerprint、labels、发生时间 | 保留，继续用于检索、审计和同指纹分析 |
| Provider 元数据与接入时路由匹配快照 | 保留 |
| Event 行、ID 与接收时间 | 保留 |
| Delivery 状态、错误、尝试次数和下次重试时间 | 保留 |
| Delivery 的 `renderedPayload` | 保留；这是实际渲染给目标的内容，不是 Event 原始载荷 |
| Delivery attempt 的结果、响应与错误 | 保留 |
| 飞书加急呼叫与接收人记录 | 保留 |
| 容器日志 | 由部署平台的日志轮转与保留策略管理，不由该设置控制 |

因此，原始载荷清理后仍可回答「事件何时到达、匹配了哪些路由、向哪些目标发送、成功还是失败」，但不能继续查看上游当时的完整 JSON 或 Header。

::: tip 原始字段已经在接入时脱敏
Tocsin 会递归替换常见敏感键并对自由文本做脱敏，再保存原始调试字段；这不是数据分类或完整 DLP 保证。不要把 `rawPayload` 当作可以公开传播的普通事件数据。
:::

## 历史表为什么会持续增长

三个主要因素会放大 SQLite 数据量：

1. 每个通过认证的 Webhook 都写入一条 Event，包括重复请求和 Provider 解析失败。
2. 一条 Event 命中多条 Route，或一条 Route 有多个 Destination 时，会为每个「Route + Destination」创建 Delivery。
3. 每次投递尝试会写入 attempt；启用电话加急时还会写入加急呼叫和接收人记录。

当前没有针对历史 Event、Delivery、attempt 或 on-call ping 的自动保留或批量清理功能。Event 与 Delivery 页面顶部的时间范围只是查询条件，不会删除窗口外的数据。例外是幂等去重键：Tocsin 按 5 分钟幂等窗口在接入时按批清理，不会随 Event 永久累积。

### 删除配置带来的级联影响

删除资源不是无损的容量清理方式。执行前必须阅读 dashboard 的影响预览，并先完成可恢复性评估。

| 操作 | 影响与保留边界 |
| --- | --- |
| 删除告警源 | 删除该 Source 的 Event、关联 Delivery、attempt、加急记录与路由引用；其他 Source 的 Event 保留，相关 Route 被收窄而不是删除。 |
| 删除路由 | 删除该 Route 关联的 Delivery、attempt 与加急记录；原始 Event 及接入时路由匹配快照保留。 |
| 删除通知目标 | 删除指向该 Destination 的 Delivery、attempt 与加急记录；原始 Event 与仍引用其他目标或来源的 Route 保留。 |

删除告警源的影响最大，也会使该来源的历史事件无法再从 dashboard 读取。详细规则见[告警源接入与生命周期](/guide/sources#删除告警源)与[路由规则与匹配](/guide/routes#告警源与通知目标的连带影响)。如果目标只是暂时停止通知，应使用静默或启停，而不是删除历史。

## 数据库空间指标

设置页的「数据库存储」面板提供只读观测值：

| 指标 | 含义 |
| --- | --- |
| 数据库体积 | SQLite `page_count × page_size`，包含已分配但未使用的页 |
| 可回收空间 | SQLite freelist 上的页大小；后续写入会优先复用这些页 |
| 事件、投递、投递尝试、加急呼叫 | 各表当前总行数 |
| 最老事件、最新事件 | 当前 Event 表的接收时间边界 |

「可回收空间」不是宿主机磁盘剩余空间，也不包含 `-wal` / `-shm` 文件、日志、备份文件或同卷内的其他数据。判断磁盘压力时必须检查数据卷实际剩余空间和各文件大小，不能只看 dashboard。

原始载荷来自 Webhook 请求体，请求体受 `TOCSIN_MAX_WEBHOOK_BYTES` 约束（默认 1 MiB，最大 10 MiB）；原始载荷的存储体积与该上限处于同一量级。规划时可用「每日 Event 数 × 平均原始载荷大小 × 保留天数」粗算，例如每天 10,000 条、平均 20 KiB、保留 30 天，约 5.7 GiB；标准化字段、路由快照、Delivery 与 attempt 另行计入。

原始载荷被替换后，旧页可能进入 freelist 并被后续写入重新利用，但 SQLite 不会自动把主数据库文件缩回。Tocsin 当前也没有提供 `VACUUM`、完整性检查或一键压缩按钮；`VACUUM` 需要独占数据库，在单进程运行中执行会阻塞或干扰正常写入。

::: warning 不要直接删除数据库文件
数据库文件同时包含配置、凭证、用户、历史和迁移台账。清理 `-wal` / `-shm`、删除主库或改写 SQLite 文件都可能造成不可恢复的数据损坏。需要离线压缩时，应停止所有写入、先完成并验证备份，再在维护窗口使用受控的 SQLite 工具，并在完成后检查 `/api/ready`、登录与最近事件。
:::

## 容量处置顺序

1. 在「数据库存储」记录当前体积、可回收空间、四类行数和最老/最新事件，作为后续比较基线。
2. 同时检查宿主机数据卷余量、主数据库、`-wal` / `-shm` 和备份目录；dashboard 不提供宿主机磁盘余量。
3. 核对当前原始载荷保留期。策略允许时缩短窗口，发送测试 Webhook 后抽查旧 Event 是否显示已清理提示。
4. 如果磁盘仍持续增长，比较一段时间前后的行数。先调查重复接入、路由扇出、失败重试和加急呼叫是否异常，再决定是否调整配置。
5. 只有在审计与恢复要求允许时，才考虑删除已废弃的告警源、路由或通知目标。删除不会自动压缩文件，释放的页会先进入可回收空间。
6. 更新备份保留策略。备份会包含备份时点仍保留的原始载荷，清理当前数据库不会追溯修改旧备份。

备份窗口与在线保留期是两个独立维度：例如原始载荷保留 7 天、每日备份保留 30 天时，部分原始载荷仍可能在备份中存在约 37 天。

## 常见现象

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 超过保留天数仍能看到原始载荷 | 没有新的 Webhook 触发清理，或后台 sweep 尚未完成 | 核对设置后发送测试 Webhook，再重新打开 Event |
| 清理后数据库体积没有下降 | 更新只释放页，不会自动缩小 SQLite 文件 | 观察可回收空间；不要直接删除数据库文件 |
| 可回收空间很高但磁盘接近耗尽 | 面板不统计宿主机余量、WAL、日志与备份 | 检查数据卷总占用并清理受控的日志/备份 |
| 最老事件日期一直不变 | Event 历史没有自动清理 | 按审计政策保留，或在确认无恢复需求后删除其告警源 |
| Delivery 详情仍能查看渲染载荷 | 原始载荷已清理，但 `renderedPayload` 属于投递记录 | 这是预期行为；按投递历史策略管理 |
| 旧备份中仍有已清理的载荷 | 备份保留的是创建时点的数据 | 对备份执行同等的数据分类、加密与过期策略 |
| 怀疑凭据曾进入 Event | 逻辑清理不保证从 WAL、空闲页、快照或备份中物理擦除 | 立即轮换对应凭据并按安全事件流程处置，不要依赖保留期 |

## 安全边界

- 原始载荷清理是记录级覆盖，不是加密擦除或磁盘安全擦除。SQLite 空闲页、WAL、文件系统快照和备份都可能保留旧内容。
- 事件证据包在导出时再次脱敏，但已经清理的字段无法恢复。清理前需要长期保存的证据必须按组织流程归档。
- 不要把源 Token、目标密码、签名密钥或未脱敏请求体写入工单、工单附件、聊天记录或公开日志。
- 备份文件应视同凭据材料保护，并设置独立于业务数据库的保留期，见[备份与恢复](/operations/backup-restore)。
