# 投递检索、生命周期与重试

Delivery 记录一次「把某个 Event 发送到某个通知目标」的工作。它保存发送结果、尝试记录和错误，是判断「告警有没有真正送达」的唯一依据。

先分清三个对象：Event 记录收到什么，Route 决定为哪些目标产生投递，Delivery 记录发送结果。`pending` 不是失败，`suppressed` 也不是网络故障。本页说明如何从事故线索定位投递，以及投递状态、重试、暂停和积压处置；路由为何命中见[路由规则与匹配](/guide/routes#查看匹配证据)，通知目标的字段与模板见[通知目标参考](/integrations/destinations)。

## 一条投递从哪里来

一条 Event 命中一条已启用路由后，Tocsin 会为该路由选择的每个通知目标各创建一条 Delivery。同一 Event 的这一组合只会创建一条；内容相同的重复入站载荷在去重窗口（默认 5 分钟）内也不再创建新投递。删除路由会连同其投递一起删除，删除前应阅读界面的影响提示。

创建时命中有效静默规则的投递直接成为 `suppressed`，不产生发送尝试，也没有外部消息回执。静默的匹配与时间窗见[告警静默与维护时段](/operations/suppressions)。

## 检索、筛选与定位

投递页同时提供结构化筛选和自由文本搜索。已知具体 Event 时，从事件详情的「投递」标签进入；只有错误文本、目标名称、路由名称或回执片段时，直接在投递页搜索。筛选条件写入 URL，刷新或分享链接会保留同一组条件；修改任意筛选后列表回到第一页。

### 结构化筛选

| 条件 | 用途 |
| --- | --- |
| 告警源、严重程度、状态 | 按 Event 来源与规范化告警字段缩小范围 |
| 通知目标、目标类型、路由 | 定位一个接收端、一类适配器，或某条路由产生的全部投递 |
| 投递状态 | `pending`、`running`、`succeeded`、`failed` 或 `suppressed` |
| 最少尝试次数 | 只看至少尝试 1、2 或 3 次的投递，便于找重试流量 |
| 回执 | 只看有外部消息引用，或没有完整引用的投递 |
| 精确指纹 | 只看某个告警指纹产生的全部投递；从事件详情「同指纹」标签一键进入，与搜索框的子串匹配不同 |
| 时间范围与时间口径 | 最近 15 分钟至 7 天；按「创建时间」或「更新时间」筛选并排序 |

「更新时间」会随重试和状态变化前移，适合查找最近仍在活动的投递；追查某次告警最初的产生时间时使用「创建时间」。时间窗在打开时固定下界，因此翻页或重新打开同一链接不会让结果持续滑动。

### 文本搜索

搜索在**同一条投递行**的可检索字段中做字面子串匹配：

- Event 的标题、消息、fingerprint、幂等键、标签与上游元数据；
- Event ID 或 Delivery ID；
- 当前最后错误、**任意一次尝试的错误**；
- 通知目标名称、路由名称与目标返回的外部消息引用。

空白分隔的多个词按 **AND** 处理，最多使用前 8 个词；每个词只需在某一个可检索字段中命中，不要求全部出现在同一列。例如 `timeout feishu` 可把一次尝试错误中的 `timeout` 与目标名称中的 `feishu` 组合起来。搜索不解析引号短语、字段前缀、OR 或通配符；`%`、`_` 与 `\` 按普通字符匹配。原始载荷、原始请求头与尝试的响应体不参与搜索。

| 手上的线索 | 建议检索 |
| --- | --- |
| 告警群里的一段投递错误 | 只输入稳定且有辨识度的错误片段，例如 `handshake timeout` |
| 错误片段与告警标签 | 组合错误词和 `prod`、`checkout` 等标签值，例如 `503 prod` |
| 飞书或 Slack 的消息引用 | 直接粘贴回执值，例如 `om_...` |
| 目标或路由名称 | 直接输入可辨认的名称片段，再叠加状态或时间筛选 |

::: tip 重试成功后仍可按早期错误找回
投递成功后，当前最后错误会被清空；但只要某次尝试曾失败，该错误仍可从投递搜索框中命中。此时列表行可能显示 `succeeded` 且没有当前错误，命中证据在详情的尝试历史中。搜索只能说明“曾经存在这段错误”，不能单独证明投递现在仍失败。
:::

## 状态与时间口径

| 状态 | 含义 | 值班时怎么读 |
| --- | --- | --- |
| `pending` | 等待 Worker 领取 | 可能正在重试退避、目标或路由已停用，或出站投递被全局暂停。不是失败，也不会因为等待而被丢弃。 |
| `running` | 已被 Worker 领取，正在发送 | 超时或进程中断会留下长期 `running`，由 Worker 按过期窗口回收。 |
| `succeeded` | 目标已接受 | 飞书与 Slack 还会校验业务码或响应体，HTTP 200 不等于成功。 |
| `failed` | 终态失败 | 保留尝试记录和最后错误；通常可以手动重试，例外见下文。 |
| `suppressed` | 按静默规则跳过 | 没有发送尝试，也没有回执；不是网络失败，不会自动补发。 |

投递详情使用三种时间口径，排障时不要混用：

| 口径 | 计算方式 | 用途 |
| --- | --- | --- |
| 排队耗时 | 创建 → 第一次尝试开始 | 判断 Worker 是否及时领取，还是目标/路由停用或全局暂停造成等待。 |
| 发送耗时 | 所有已完成尝试的耗时之和 | 目标响应速度；不包含排队和重试退避。 |
| 端到端耗时 | 创建 → 终态 | 告警从产生投递到最终有结果的总时长。 |

单次尝试的「耗时」只是这次发送的耗时，不包含在队列中等待或两次尝试之间的退避时间。

## 自动重试与退避

每次投递默认最多尝试 3 次。失败后同时满足以下条件才会自动重试：

- 目标适配器把这次错误判定为可重试。
- 已尝试次数还没有达到该投递的上限。

退避从 30 秒开始按 2 倍递增，单次上限 15 分钟。默认 3 次上限下，实际间隔是第一次失败后 30 秒、第二次失败后 60 秒；用完最后一次尝试后转为 `failed`。

### 按响应判定是否重试

不同通知目标对「失败」的判定不一样。先按下面的分组判断会不会自动重试，再决定是等待退避还是修配置。

**会重试**

- 连接超时、DNS/TLS 错误或其他网络错误。传输层没有拿到响应，确认目标可达后等待退避即可。
- HTTP `408`、`409`、`425`、`429`、`5xx`。目标暂时不可用或限流；`429` 还要检查目标侧配额，Tocsin 只按退避重试，不会自动放慢全局发送速率。
- 飞书返回下文列出的可重试业务码。包括限流、token 失效和接收人未读加急过多。
- 适配器抛出未分类异常。按可重试处理以便跨过瞬时故障；若同一目标反复出现，应按缺陷排查。

**不会重试**

- 其他 HTTP `4xx`。目标明确拒绝，例如地址错误、鉴权失败或载荷不被接受；按错误文本修正目标配置后手动重试。
- Slack 返回 `2xx` 但响应体不是 `ok`。目标已收到请求但拒绝处理，常见于 Webhook 被撤销、频道归档或应用被移出频道；到 Slack 侧核对后修正配置，再手动重试。
- 飞书返回 `2xx` 且业务码非 0，且不属于可重试集合。未知业务码按不可重试处理。
- 发送前配置解析失败。例如模板渲染错误、目标配置不合法或凭据未能解析；修正配置后手动重试。

**按目标类型补充**

- 通用 Webhook、邮件网关：返回 `2xx` 即视为成功，响应体不参与判定。
- 飞书：非 `2xx` 时先看业务码；业务码不可重试时再按 HTTP 状态判定，因此 `5xx` 仍会重试。

飞书的业务码优先于 HTTP 状态：平台常以 HTTP `400`（自定义机器人甚至以 `200`）返回业务拒绝，所以不能只看状态码。会重试的业务码只有：

- `99991400`：请求触发频率限制。
- `11232`、`11233`：发送消息触发系统频率限制。
- `230023`：接收人的未读加急消息过多，读完后可以再次加急。
- `99991661`、`99991663`、`99991665`：`tenant_access_token` 失效；重试时会重新获取 token。

其余非 0 业务码一律不重试，例如未开启机器人能力、机器人不在群内、群已解散、加急额度耗尽或接收人已离职。错误文本会保留平台原始 `code`、`msg` 和可执行的修复提示；按提示在飞书侧修复后，对当前失败投递手动重试。

不可重试的错误直接失败，不再消耗后续尝试。修复配置只影响之后的投递，当前失败记录仍需手动重试。

等待重试的投递回到 `pending` 并显示下次重试时间。即使已经排到重试，Worker 在真正领取时仍会重新检查静默规则：此时命中静默的投递转为 `suppressed`，已有的失败尝试保留，但不会继续发送。

## 手动重试

在投递列表或详情页对 `failed` 投递执行「重试投递」：

- 投递重新入队，下次尝试设为当前时间并清除最后错误。如果尝试次数已到上限，上限会自动提高 1，因此手动重试总能再发一次。
- 发送使用通知目标的当前配置。端点在失败后被修改时，重试按新配置发送。
- 不会重新匹配路由，不会创建新的 Event，也不会影响同一 Event 上的其他投递。

::: danger 目标已受理但记录失败的投递禁止重试
如果目标已经接受消息、但 Tocsin 记录成功状态失败，投递会以失败终态显示，并明确说明目标已受理。界面会禁用重试：重发会让值班人员收到重复通知。先到目标端核对消息是否已经到达，不要绕过界面直接重发。
:::

手动重试不是历史补投。要给「当时没有创建投递」的路由与目标组合补投，使用 Event 页的「预览历史匹配」；它按补投时刻的规则评估，不能替代投递重试。两者的边界见[路由规则与匹配](/guide/routes#查看匹配证据)。

## 重试与重复通知风险

投递是「至少一次」语义，不是「恰好一次」。发送请求交给目标后，Tocsin 只能记录自己收到的响应；请求在超时、连接中断或进程退出时有没有被目标处理，本地无法确认。重试保证尽量不丢，也意味着同一 Event 可能被目标收到多次。

Tocsin 不会给 Slack 或飞书发送幂等键，重试时也不会查询目标端是否已有同一消息；通用 Webhook 只发送固定的 `Content-Type` 和运营者配置的 Header，不会自动附加幂等 Header。需要机器级去重时，应把告警送到能自行幂等的接收端。

### 可能重复发送的路径

- **超时后的自动重试**：目标可能已受理，但响应没有在默认 10 秒出站超时内回到 Tocsin。Tocsin 看到传输超时并安排重试，目标会收到第二条。超时由 `TOCSIN_DESTINATION_TIMEOUT_MS` 统一控制，见[环境变量与运行时配置](/operations/configuration)。
- **`5xx`、`429` 后的自动重试**：接收端可能已经入队或处理了部分请求，随后才返回错误或限流。重试按退避再发一次。
- **Worker 中断后的回收与重试**：进程重启或 OOM 终止时，尝试停在 `running`；超过 5 分钟按「结果未知」回收。若还有剩余尝试次数，会立即重新排队等待下一次尝试，而目标可能已经收到原请求。
- **手动重试**：除「目标已受理」外，界面不判断目标是否曾经收到。超时类失败可能是假阴性，重试就是再发一次。
- **历史补投**：只补该 Event 在路由与目标上缺失的 Delivery，不会重发已有投递；但补出来的投递对接收端是真实的新请求，可能表现为重复告警。

### 不会重复发送的情况

- 同一 Event 与同一 `路由 + 目标` 组合只有一条 Delivery；历史补投会跳过已存在的组合。
- 同一来源、相同幂等键、同一 `路由 + 目标` 在去重窗口（默认 5 分钟）内重复到达时，不会创建新的投递通知；Event 本身仍会各自记录。
- 幂等键由告警解析器生成：Grafana、Alertmanager 兼容来源、Uptime Kuma 与通用 Webhook 默认使用载荷哈希；通用 Webhook 还会优先读取载荷中的 `idempotencyKey`、`requestId`、`eventId` 等字段。
- 因此，上游重发**完全相同**的载荷不会重复通知。对使用载荷哈希的来源，载荷任一字节变化（典型是时间戳）都会得到新的幂等键，按新告警投递。这类重复来自上游重发，不是 Tocsin 重试。
- 标记为「目标已受理」的失败投递禁止重试；静默跳过的投递不会发送，窗口结束后也不会补发。

### 两种「结果未知」怎么处理

它们都表示 Tocsin 没有拿到确定的发送结果，但处置方式不同：

- **目标已受理，记录成功失败**：错误文本以 `The destination accepted the alert, but recording success failed` 开头，界面禁用「重试投递」。目标已经收到告警，先到目标端核对；不要绕过界面直接改库重发。
- **尝试结束但没有记录结果**：错误文本包含 `the target may or may not have received the alert`。还有尝试次数时会自动重试；退化为终态时，界面提示先向目标核实再手动重试。这类投递仍可手动重试，但重试可能就是第二条通知。

### 让接收端可以去重

- **通用 Webhook**：默认信封包含 `eventId`、`source.id` 与 `destination.id`，接收端应以 `eventId` 或 `eventId + destination.id` 作为幂等键。使用 `json_payload` 自定义模板会替换整个信封，默认字段不再存在；需要幂等时必须在模板中显式保留事件 ID 变量 `<code v-pre>{{event.id}}</code>。字段说明见[通知目标参考](/integrations/destinations#通用-webhook)。
- **邮件网关**：按 `metadata.eventId + metadata.destinationId` 建立幂等键，重复请求返回 `2xx` 并跳过第二次发送；用 `409` 表示重复会触发 Tocsin 继续重试。契约见[邮件网关接入与验收](/integrations/email-gateway#超时与重试)。
- **Slack 与飞书**：卡片里的 Event ID 只供人读，没有机器可读的调用方幂等键。重试后收到两条卡片属于预期，不要当成 Tocsin 缺陷；需要机器级去重时，改用可自建幂等的通用 Webhook 或邮件网关。
- **不要用 fingerprint 当投递幂等键**：fingerprint 是告警身份，同一告警的多次通知会共享它，按它去重会吞掉后续真实通知。要抑制反复触发的同一告警，使用静默规则的 `fingerprints` 匹配维度，见[告警静默与维护时段](/operations/suppressions)。

## 全局暂停出站投递

设置页的「暂停出站投递」是实例级急停开关，适合上游大面积故障、目标服务维护或通知风暴期间使用。

暂停期间：

- Worker 不领取任何任务，队列原样保留；投递不会因此变成失败，也不会被丢弃。
- 通知目标的测试动作绕过队列立即真实发送，暂停不能阻止手动测试消息。
- 电话加急使用独立队列，不受该开关影响；但排队中的投递被暂停时，自动加急会被推迟到恢复之后，见[飞书应用与电话加急](/integrations/feishu-app#去重与重试)。
- 投递页顶部显示暂停提示、恢复后将被领取的积压数量，以及最早一条已等待多久。

恢复后 Worker 按下次重试时间（没有则按创建时间）顺序领取积压。恢复前先确认目标可达、积压规模符合预期；积压很大时会连续占用多个 Worker 批次。设置页会记录最近一次暂停的开始、结束时间和操作者，可作为变更审计证据。

暂停状态是实例运行态：可移植配置的导出与导入都不包含它，见[可移植配置参考](/operations/portable-config#包含与不包含)。它也与停用路由或目标不同——后者只影响特定规则或目标，并会在投递页显示「投递已滞留」提示。

## 队列滞留与积压

Worker 只领取同时满足以下条件的 `pending` 投递：

- 通知目标已启用；
- 投递关联的路由仍存在且已启用（没有路由关联时不要求）；
- 已到下次重试时间；
- 尝试次数未达到上限。

因此，停用通知目标或路由会让相关投递停在 `pending`。投递详情会显示「投递已滞留」并指明是目标还是路由停用；重新启用后自动继续，不需要重建投递。删除目标或路由会级联删除投递，而不是保留成滞留状态。

停用告警源是接收侧开关：它拒绝新的 Webhook，但不会暂停已经入队的投递。上游停发后仍有在途投递时，不要误以为停用告警源会清空队列。

## Worker 与手动运行

投递由应用进程内的投递 Worker 异步执行，没有独立服务。默认每 5 秒轮询一次，每批最多领取 10 条；超过 5 分钟仍处于 `running` 的尝试会被视为进程中断，回收为失败并注明发送结果未知。若还有剩余尝试次数，会立即重新排队。相关阈值可用 `TOCSIN_WORKER_INTERVAL_MS`、`TOCSIN_WORKER_BATCH_SIZE` 和 `TOCSIN_WORKER_STALE_RUNNING_MS` 调整，范围与取舍见[环境变量与运行时配置](/operations/configuration)。

投递页的「运行投递工作进程」会立即执行一批（最多 10 条），用于验证配置或推动积压。它不改变队列规则：全局暂停时按钮禁用，待发送投递仍受目标/路由启停和静默约束。

设置页的「后台工作进程」是只读状态面板，展示 Worker 最近状态、上一批的领取、回收、成功、失败和重试数量，以及最后错误。确认「Worker 是否在工作」时先看这里，再看容器日志；日志类别、request id 关联和健康检查的区别见[日志与可观测性](/operations/observability)。

## 投递详情与证据

投递详情集中展示排障所需的上下文：

- 原始载荷与渲染后的 payload。原始载荷按设置中的保留天数清理，渲染 payload 继续保留，页面会标注已清理。
- 尝试记录：每次尝试的状态、HTTP 状态、脱敏后的错误与响应体，以及开始、结束时间和耗时。
- 通知目标元数据：读取目标的当前配置，并提示目标是否在本次投递后被修改。
- 路由证据：按投递当时的规则展示；如果当前规则已不再命中，页面会说明本次投递仍按当时规则执行。
- 回执：目标返回的外部消息引用，可复制到工单或上游系统检索；列表的「回执」列和筛选器使用同一字段。

「下载证据包」导出脱敏后的 JSON，文件名形如 `tocsin-delivery-<id>-<时间戳>.json`，包含 schema 版本、导出时间与投递详情，适合附到事件单或交给第二人复核。导出字段已经脱敏，但仍应按内部排障材料管理，不要公开。

## 值班检查清单

| 现象 | 优先判断 | 处理 |
| --- | --- | --- |
| `pending`，有下次重试时间 | 正常退避 | 等到时间或手动运行 Worker，不要重复触发操作。 |
| `pending`，显示「投递已滞留」 | 目标或路由停用 | 按变更计划重新启用；确认停用是预期行为。 |
| 大量 `pending`，页面顶部暂停提示 | 全局暂停 | 在设置页恢复投递；先确认积压规模和目标状态。 |
| `running` 长时间不变 | Worker 中断或重启 | 等待过期回收（默认 5 分钟）；错误注明发送结果未知时，先向目标核实再决定是否重试。 |
| `failed`，有重试按钮 | 可重试失败 | 修复目标配置并测试成功后手动重试。 |
| `failed`，提示目标已受理 | 成功状态未记录 | 禁止重试；到目标端核对消息是否已经到达。 |
| 同一告警收到多条通知 | 重试或上游重发 | 对比投递尝试记录与同 fingerprint 的 Event 数量；接收端按 `eventId` 去重，不要再次手动重试。 |
| `failed`，错误为模板或配置 | 不可重试 | 修正模板或配置；当前记录仍需手动重试。 |
| `suppressed` | 命中静默 | 查看静默原因与窗口；不会自动补发，等待新 Event。 |
| 积压持续增长 | 目标故障或 Worker 未运行 | 检查 Worker 状态、目标连通性和通知目标的投递健康数据。 |
