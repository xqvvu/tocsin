# 告警风暴与大面积误报的处置顺序

告警风暴里常见的二次事故不是漏发，而是处置动作本身：为了止噪删除路由、停用告警源，结果既丢掉证据，也把真实告警一起压住。本页给出一个可按时间线执行的顺序：先分类，再选影响面最小的急停手段，最后有序恢复并核对漏告警。

各开关的完整机制不在这里重复：静默规则见[告警静默与维护时段](/operations/suppressions)，全局暂停与积压见[投递检索、生命周期与重试](/operations/deliveries#全局暂停出站投递)，告警源启停见[告警源接入与生命周期](/guide/sources#停用与重新启用)，路由启停见[路由规则与匹配](/guide/routes)，电话加急见[飞书应用与电话加急](/integrations/feishu-app#去重与重试)。

::: danger 先确认告警是假的
「量大」不等于「误报」。如果上游可能真的在报故障，优先收窄通知范围（静默或停用单个渠道），不要停用告警源或全局暂停。停用告警源会让这段时间完全没有 Event 证据；全局暂停会把真实告警一起压住。
:::

## 先判断这是哪一种风暴

先看 dashboard 顶部横幅：已有生效静默、全量静默或全局暂停时，先确认这是不是上一班已经采取的动作，不要重复处置。

| 类型 | 看哪里 | 典型证据 | 常见根因 |
| --- | --- | --- | --- |
| <span style="white-space: nowrap">入站风暴</span> | Event 列表 15 分钟窗口的总数、来源与「同指纹」 | 事件数陡增；同一指纹反复出现，或大量不同指纹同时出现 | 上游重发、聚合失效、采集规则过宽、上游压测 |
| <span style="white-space: nowrap">重试放大</span> | Delivery 列表的 `pending`（带下次重试时间）、`failed`、尝试次数与目标 | 事件不多，但到同一目标的尝试次数和错误持续增长 | 目标 `5xx`、`429`、超时或网络故障 |
| <span style="white-space: nowrap">电话风暴</span> | Delivery 详情的「电话加急」表、目标的排队数量 | 多个 fingerprint 的 ping 同时派出或排队 | 大量不同告警通过自动加急门槛 |

判断重复发生用 Event 详情的「同指纹」标签：统计范围是同一告警源、完全相同 fingerprint 的更早事件，可下钻到事件列表和投递列表。见[事件检索与证据](/guide/events#判断是否重复发生)。

::: warning 自动加急只对「同一告警」去重
同一 fingerprint、同一目标、同一呼叫对象在 5 分钟内不会重复拨打；不同 fingerprint 之间不会互相去重。因此「很多条不同的误报告警」仍可能变成电话风暴，静默规则也要按告警源、标签或时间窗收口，而不是只按一个指纹。
:::

## 处置原则

1. **先窄后宽**：静默规则 → 停用路由 → 停用通知目标 → 停用告警源 → 全局暂停。能用一条静默解决的问题，不要动实例级开关。
2. **停止发送不等于停止接收**：停用告警源会拒绝 Webhook，且不保存 Event；停用路由、停用目标、全局暂停都保留 Event 与匹配证据。
3. **可逆优先**：不要为了止噪删除告警源、路由或通知目标。删除会级联删除投递，且不会保留可恢复的配置。停用、静默、暂停都是可逆的。
4. **一次只改一个开关**：每改一项，记录时间、范围、操作者与恢复条件。全局暂停会自动记录操作者和暂停区间；静默规则会保存原因与命中记录；停用操作没有自动审计，必须在事故频道里自己记。
5. **恢复也要按顺序**：先修根因并验证目标，再恢复发送，最后核对积压、漏告警与重复通知。

::: tip 不要把重启当作清队列
重启不会清空 SQLite 队列；进程中断只会让 `running` 投递在过期后被回收重试。清库、删 WAL 或删路由都会丢失证据。队列的正确出口是恢复发送，或用一个覆盖积压的静默让它们以 `suppressed` 结束。
:::

## 五种急停手段的影响面

### 会立刻停止什么

| 手段 | 停止什么 | Event 与匹配证据 | 已在队投递 | 自动电话 |
| --- | --- | --- | --- | --- |
| <span style="white-space: nowrap">静默规则</span> | 匹配范围内的新投递 | 完整保留；投递带原因快照 | 认领时重新判定，命中转 `suppressed` | 不发起；被静默的投递不能手动加急 |
| <span style="white-space: nowrap">停用路由</span> | 该路由的新匹配与新投递 | Event 保留；快照只显示「路由已停用」，不再评估具体条件 | 停在 `pending`，重新启用后继续 | 不会为未发送的投递发起；已排队的 ping 不受影响 |
| <span style="white-space: nowrap">停用通知目标</span> | 该目标的卡片发送与加急派发 | 完整保留 | 该目标的投递停在 `pending` | 已排队的 ping 也停止派发，重新启用后继续 |
| <span style="white-space: nowrap">停用告警源</span> | 该源的新 Webhook | **不保存 Event**；请求返回 `403` | 不受影响，继续发送 | 已产生的 ping 不受影响 |
| <span style="white-space: nowrap">全局暂停</span> | 所有出站卡片投递的领取 | 完整保留 | 原样保留，恢复后按顺序领取 | 已排队的 ping 仍会派发；不会产生新的自动 ping |

### 恢复动作与主要代价

| 手段 | 恢复动作 | 主要代价 | 适合 |
| --- | --- | --- | --- |
| <span style="white-space: nowrap">静默规则</span> | 到期自动恢复，或提前关闭 | 窗口内的新告警也一起静默；结束后不补发 | 已知误报、计划维护、单个指纹或标签的噪声 |
| <span style="white-space: nowrap">停用路由</span> | 重新启用 | 积压集中发送；停用期间的真实告警不会产生投递 | 一条路由规则明显过宽，或只需要停一条投递路径 |
| <span style="white-space: nowrap">停用通知目标</span> | 重新启用 | 卡片积压与排队电话集中释放，旧 ping 可能已无意义 | 目标故障、渠道限流、电话风暴 |
| <span style="white-space: nowrap">停用告警源</span> | 重新启用 | 停用期间的告警没有 Event，也不会自动补收 | 上游失控刷屏且数据不需要保留，或临时切断问题发送方 |
| <span style="white-space: nowrap">全局暂停</span> | 确认后恢复 | 所有渠道一起停；恢复时积压与自动加急集中 | 范围不明、多个渠道同时受影响、需要一键止损 |

### 静默规则

最窄的手段，优先使用。可以从事件详情「静默此指纹」、事件标签「静默此标签」、路由行「临时静默此路由」、通知目标行「临时静默此目标」创建，减少手填范围错误。

- 匹配条件为空表示静默全部告警，保存前有二次确认，生效后 dashboard 顶部显示「全量静默生效中」。
- 静默会同时压住普通消息和自动电话提醒；已经发出的电话无法撤回。
- 窗口结束不会补发窗口内被跳过的通知；需要复盘时查看规则详情的「已静默通知」。
- 不确定范围时，先用一个指纹或一个标签的小范围规则，再逐步扩大；不要一上来创建全量静默。

### 停用路由

停用后，新事件不再匹配这条路由，也不会创建新投递；已经在队但尚未发送的投递会停在 `pending`，重新启用后继续。

- 停用期间接入的 Event 仍会保存快照，但该路由的检查结果只显示「路由已停用」，不再评估具体条件。复盘时不要用它判断规则本来是否应该命中。
- 停用路由不会撤回已经排出的电话加急。电话正在响时，应改为停用对应的通知目标。
- 如果只是临时安静一段时间，使用路由行的「临时静默此路由」，这样每条被跳过的投递都会留下 `suppressed` 证据。

### 停用通知目标

这是唯一能同时停掉「即将发出的卡片」和「已排队的电话」的目标级开关。电话正在响时，先停用对应的飞书目标，再分析告警本身。

- 同一路由上的其他通知目标不受影响，仍会正常发送。
- 确认框会列出受影响告警源（含「所有告警源（含后续新增）」的情形）、排队投递数与「自动加急也会停止」提示；电话正在响时先核对这些区块再确认，口径见[停用与删除前的影响确认](/integrations/destinations#停用与删除前的影响确认)。
- 重新启用会同时释放卡片积压和排队中的 ping；界面没有取消排队 ping 的操作，恢复前先确认这些电话是否仍然需要拨出。
- 目标停用期间仍可使用目标行的「测试」验证端点和凭证；测试绕过队列与全局暂停，也不会创建 Event。

### 停用告警源

停用后，Tocsin 会在凭据校验之前拒绝该源的新 Webhook，返回 `403`，不会创建 Event、路由匹配或投递。已经入队的投递继续发送。

- 上游通常会把这视为失败并重试或补发；停用时间越长，上游侧积压越多。
- 重新启用后不会自动补收停用期间的告警，需要上游重发。对账依据是上游发送日志和 `tocsin.intake` 中 `reason=source_disabled` 的警告。
- 需要保留 Event 证据时，不要用停用告警源止噪，改用静默规则或停用路由。

### 全局暂停

设置页的「暂停出站投递」是实例级开关。暂停期间 Worker 不领取任何卡片投递，队列原样保留；通知目标的测试动作绕过队列立即真实发送；独立的加急队列不受暂停影响。

- 投递页顶部会显示暂停提示、恢复后将被领取的积压数量，以及最早一条已等待多久。
- 设置页记录最近一次暂停的开始、结束时间和操作者；暂停状态不进入可移植配置。
- 恢复需要确认：飞书应用模式且启用自动加急的目标，会对排队期间仍处于触发中的告警重新呼叫接收人；暂停越久，恢复时的电话越集中。
- 全局暂停是最后手段。使用前先确认没有更窄的开关能覆盖问题范围，恢复前先确认目标和积压。

## 按时间线处置

### T+0 确认范围（2 分钟）

1. dashboard 顶部：是否已有生效静默、全量静默或全局暂停。
2. 事件页选 15 分钟：看总数、主要来源，并对代表事件打开「同指纹」。
3. 投递页按 `pending`、`failed` 和时间窗筛选：确认集中在哪些目标、尝试次数是否在增长。
4. 通知目标列表：排队数量、近 24 小时失败数。
5. 设置 → 后台工作进程：确认投递与加急 Worker 没有进入「失败」。

先回答三个问题：告警可能是真的吗？影响一个源、一条路由、一个目标，还是全实例？电话是否已经在响？

### T+2 选择最小急停

| 判断 | 首选 | 入口 | 备注 |
| --- | --- | --- | --- |
| 同一个 fingerprint 反复出现 | 静默此指纹 | Event 详情 →「静默此指纹」 | 只影响这一条告警，证据最完整 |
| 某个服务或标签的已知噪声 | 静默此标签 | Event 标签 →「静默此标签」 | 注意标签匹配区分大小写 |
| 一条路由范围过宽 | 临时静默此路由，或停用路由 | 路由行操作 | 需要逐条 `suppressed` 证据就用静默 |
| 一个渠道故障或电话正在响 | 停用通知目标 | 通知目标行操作 | 同时停止已排队 ping 的派发 |
| 一个上游失控刷屏且不需要 Event | 停用告警源 | 告警源行操作 | 停用期间没有 Event，之后无法补查 |
| 范围不明或多个渠道同时受影响 | 全局暂停 | 设置 → 暂停出站投递 | 最后手段，恢复时注意集中补呼 |

::: danger 电话已经在响
先停用对应的飞书通知目标。只做全局暂停时，已经排队的 ping 仍会继续拨出；停用路由也不会撤回它们。停用目标后，未派发的 ping 会停在队列里，重新启用前必须核对。
:::

### T+5 固定证据

- 写清开始时间、影响范围、操作者和恢复条件，发到事故频道。
- 记下代表性 Event ID、Delivery ID、最早一条 `pending` 的等待时间和当前积压数量。
- 全局暂停会自动记录操作者和区间；静默规则会保存原因和命中记录；停用操作没有自动审计，必须手工记录。
- 不要批量下载证据包。选几条代表性 Event 或 Delivery 导出即可，避免在风暴中放大数据库和网络压力。
- 停用告警源期间没有 Event，记下起止时间，供事后与上游发送日志对账。

### T+10 修复根因

| 根因 | 处理 | 验证 |
| --- | --- | --- |
| 上游重发或聚合失效 | 在上游停止重发、修正聚合或重复间隔 | 发一条 canary，只应产生一个 Event 和一组投递 |
| 路由规则过宽 | 收窄条件；恢复前不要删除旧路由 | 用测试事件核对 Event 的逐条件匹配证据 |
| 目标故障、限流或凭证失效 | 修复端点、凭证或配额 | 目标行「测试」；测试绕过队列与暂停，可直接验证 |
| 静默规则误配或范围过大 | 关闭误建规则，必要时改为更窄的规则 | 确认顶部提示消失，新 Event 产生正常投递 |
| 同一告警重复通知 | 上游降低重复发送频率；接收端按 `eventId` 去重 | 对比同指纹的 Event 与 Delivery 尝试记录 |

### T+20 有序恢复

1. **先验证目标**：修复后用目标行的「测试」验证端点与凭证。测试绕过队列和全局暂停，停用状态下也可执行。
2. **核对积压**：投递页顶部横幅显示可领取数量与最早等待时间，目标列表显示排队数量。积压过大时分批恢复。
3. **决定积压是否仍要发送**：
   - 告警仍然有效：直接恢复。
   - 告警已经恢复或过期：先创建一个覆盖积压范围的静默规则，再恢复发送。Worker 认领时会把积压转成 `suppressed`，不会真实发出，原因与证据仍保留。静默窗口要覆盖整个排空过程，确认积压清零后再关闭。不要用删除路由或目标来清队列。
4. **按接收链路到发送链路恢复**：先恢复告警源（如已停用），再恢复路由与通知目标，最后解除全局暂停。每恢复一项，确认没有新的错误再继续。
5. **用 canary 验证**：从上游发一条测试告警，确认 `202`、Event 生成、路由命中、Delivery `succeeded`；电话目标用小范围手动加急验证。
6. **盯第一批积压**：确认没有集中失败；飞书目标注意自动加急是否按预期补呼。

### T+30 核对漏告警与重复

| 问题 | 怎么查 | 结论 |
| --- | --- | --- |
| 停用告警源期间的告警 | 上游发送日志与 `tocsin.intake` 中 `reason=source_disabled` 的记录按 `sourceId` 和时间对账 | 没有 Event；需要上游补发 |
| 停用路由期间接入的告警 | Event 列表有记录，但没有为该路由创建 Delivery；重新启用不会自动补投 | 需要时用「预览历史匹配」逐条补投，内容可能已经过期 |
| 停用通知目标期间的告警 | Event 列表有记录；恢复后检查对应 Delivery 是否仍为 `pending` 或已发送 | 恢复后自动补发，内容可能已经过期 |
| 静默期间的告警 | 静默规则详情的「已静默通知」 | 不会补发；确认被静默的确实是噪声 |
| 重复通知 | 同指纹下的事件、投递尝试记录与目标回执 | 来自重试或上游重发；接收端按 `eventId` 去重 |
| 电话 | 投递详情的「电话加急」表：`scheduled`、`fired`、`failed` | 停用目标期间排队、恢复后集中派发；没有取消入口 |

停用路由期间接入、且没有为该路由创建投递的 Event 不会自动补投。确认真实且仍然有效的告警，可以在重新启用路由后，从 Event 详情使用「预览历史匹配」补投缺失的目标组合；该操作只扫描最近 20 条事件，不能全量补投，也不要对风暴期间的噪声批量执行。

## 恢复时的三个风险

### 恢复突发

积压按下次重试时间或创建时间顺序领取。全局暂停恢复时，仍处于触发中的飞书应用模式告警会补呼接收人。恢复前确认积压规模、最早等待时间和值班是否在线；积压很大时，预期连续占用多个 Worker 批次。

### 过期告警

积压投递携带的是当时的告警内容。上游后续发送的 `resolved` 是新的 Event，不会取消已经排队的旧投递。对已经恢复的告警，按 T+20 先用静默让它们以 `suppressed` 结束，避免恢复后把过期告警再发一遍。

### 重复通知

重试与恢复都是「至少一次」语义。接收端按 `eventId` 或 `eventId + destinationId` 去重；不要在恢复期间对 `failed` 批量手动重试，除非已经确认目标没有收到。细节见[重试与重复通知风险](/operations/deliveries#重试与重复通知风险)。

事故结束、把控制权交回日常值班前，按[值班交接与通知链路验收](/operations/oncall-handoff)记录暂停、静默、停用目标、积压和电话核实结果。不要让下一个班次在不知情的情况下恢复积压或重新启用目标。

## 不要做的事

- 不要删除告警源、路由或通知目标来止噪。删除会级联删除投递，且无法恢复到删除前的配置。
- 不要重启进程、清库或删除 WAL 来清队列。队列不会因此消失，只会丢失证据。
- 不要在风暴中批量手动重试 `failed` 投递，可能把一条告警放大成多条通知。
- 不要用 fingerprint 作为接收端的投递幂等键；同一告警的多次真实通知会共享它。
- 不要只看消息群判断恢复。先确认 Event、Delivery 和目标回执，必要时用 canary。
- 不要在一次处置中同时改多个开关；否则事后无法判断哪一个动作生效。

## 值班检查清单

| 现象 | 立即动作 | 避免 |
| --- | --- | --- |
| 手机持续响，多个告警同时加急 | 停用对应飞书目标，核对 fingerprint 分布 | 只做全局暂停，已排队的 ping 仍会拨出 |
| 同一个 fingerprint 刷屏 | 从 Event 详情静默此指纹 | 删除或停用整条路由 |
| 多个来源大量不同告警 | 判断真假；按告警源或标签创建静默 | 直接全局暂停后忘记恢复 |
| 一个目标大量等待重试或 `failed` | 停用该目标，修复端点后用「测试」验证 | 对失败投递批量手动重试 |
| 群消息重复但事件不多 | 看尝试记录和上游重发 | 再次手动重试 |
| 恢复后突然大量通知 | 预期积压，分批核对目标与最早等待时间 | 立刻再次暂停，掩盖真实失败 |
| 恢复后电话集中 | 自动加急对仍 firing 的告警补呼；提前告知值班 | 在交接前恢复电话目标 |
| 停用告警源后仍有在途通知 | 这是预期行为；已入队投递会继续发送 | 误以为停用告警源会清空队列 |
