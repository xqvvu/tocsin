# 事件检索与证据

Event 是 Tocsin 对接入告警的持久记录。它保存 Webhook 被接收时的原始调试信息、Provider 规范化后的告警字段，以及当时的路由匹配快照。Delivery 是后续按 Route 与 Destination 产生的外发任务；有 Event 不等于有 Delivery，`202 Accepted` 也不代表目标已经收到通知。

本页按一次真实排障的顺序说明：先找到事件，再核对解析和路由，最后检查投递、导出证据或补投。

## 一次完整的排查路径

1. 在「事件」页选择事故时间窗，再按告警源、严重程度、状态、通知目标及其投递结果缩小范围。
2. 先看列表中的「解析失败」「未匹配路由」和投递计数（状态徽标可点击下钻），判断问题发生在接入、匹配还是投递阶段。
3. 打开事件详情，在「标准化字段」确认实际告警内容，在「路由匹配」读取检查证据。
4. 在「投递」标签打开对应 Delivery，继续查看尝试记录、错误与重试状态。
5. 需要复盘或交接时下载脱敏证据包；需要补发缺失目标时使用「重新匹配」。

事件列表和筛选条件写入 URL，刷新或分享链接后会保留同一组条件。列表默认最新事件在前。

## 定位事件

事件页提供以下筛选维度：

| 条件 | 用途 |
| --- | --- |
| 告警源 | 把范围限定到一个上游系统或一个 Source 实例 |
| 严重程度 | 可同时选择 `critical`、`warning`、`info`、`unknown` 中的多个值 |
| 状态 | 可同时选择 `firing`、`resolved`、`unknown` 中的多个值 |
| 通知目标 | 只看达成某个目标的事件，或反向查找没有该目标投递的事件 |
| 目标投递 | 选择「有该目标的投递」或「无该目标的投递」；后者用于查覆盖缺口 |
| 目标投递结果 | 只看发往所选目标的投递处于成功、失败、待处理、运行中或已抑制状态的事件 |
| 投递结果 | 跨任意目标：完全未产生投递，或至少有一条成功、失败、待处理、运行中、已抑制的投递 |
| 投递覆盖 | 对已经产生投递的事件，[区分全部送达、部分送达与无人送达](#核对多目标投递覆盖) |
| 解析结果 | 只看 Provider 解析失败的审计 Event，或排除这类 Event；`解析成功` 不等于命中路由或成功投递 |
| 时间范围 | 最近 15 分钟、1 小时、6 小时、24 小时或 7 天 |
| 搜索 | 标题、消息、指纹、幂等键、标签、上游元数据、Event ID、关联 Delivery ID 或外部消息引用 |

### 多值筛选怎么组合

严重程度和状态是复选框筛选器。同一维度内按 **OR** 组合，跨维度与其它条件按 **AND** 组合。例如同时选择 `critical`、`warning`，再选择 `firing`，只返回严重程度为 critical 或 warning 且仍在触发中的 Event。

筛选条件写入一个逗号分隔的 URL 参数，便于复制和分享：

```text
/events?severity=critical,warning&status=firing&range=1h
```

只选一个值的旧链接仍然有效；取消某个值会从参数中移除，清空该维度的全部勾选等于“不限”，不会把列表变成“匹配不到任何事件”。筛选 chip 显示已选值，点击它会清除整个维度。手工编辑 URL 时，未知值和重复值会被忽略；如果只剩未知值，该维度按未筛选处理。

## 目标投递结果怎么组合

「通知目标」「目标投递」「目标投递结果」描述的是同一组目标投递，不能只选其中一层就推断具体结果：

| 选择 | 返回的事件 | 典型用途 |
| --- | --- | --- |
| 只选通知目标，目标投递保留「有该目标的投递」 | 至少有一条到该目标的 Delivery；`pending`、`running`、`failed`、`succeeded` 或 `suppressed` 都算 | 确认某目标是否被路由覆盖 |
| 通知目标 + 目标投递「无该目标的投递」 | 没有任何到该目标的 Delivery，包括未命中路由、路由未选择该目标，或 Event 完全没有投递 | 查目标覆盖缺口 |
| 通知目标 + 目标投递「有」+ 目标投递结果「该目标投递失败」 | 至少有一条到所选目标、当前状态为 `failed` 的 Delivery | 判断某个渠道本身是否失败 |
| 只设投递结果「失败」，不设通知目标 | 任意目标上至少有一条 `failed` Delivery | 做跨渠道的广泛扫描，不用于定位单个目标 |

同一个 Event 可能通过多条路由向同一个目标产生多条 Delivery。只要其中一条处于所选目标状态，事件就命中；事件列表按 Event 计数一次，不会因多条 Delivery 重复出现。目标投递结果读取的是 Delivery 的**当前状态**，不是历史 attempt：一次失败后重试成功的投递当前为 `succeeded`，不会命中「该目标投递失败」；要追查历史错误，转到投递页搜索任意一次尝试的错误。

「投递结果」与「目标投递结果」是不同维度，同时设置时按 AND 组合：

- **投递结果**只问「任意目标是否出现过该状态」，适合发现告警扇出中是否存在失败。
- **目标投递结果**只问「所选目标本身是否处于该状态」，避免把「Pager 失败、邮件成功」误读成「Pager + 失败」。

目标投递结果只在已选通知目标、且目标投递为「有」时出现。选择「无该目标的投递」后，该控件会隐藏并清除已有状态，因为“没有到该目标的投递”和“该目标投递失败”不能同时成立。只把 `destinationOutcome` 手工留在 URL 而不带 `destinationId` 时，条件会在 URL 边界被丢弃。

典型链接如下。把占位 ID 替换为 dashboard 下拉框中实际目标对应的 ID；时间范围可继续叠加：

```text
/events?destinationId=<pager-destination-id>&destinationOutcome=failed&range=1h
```

这条链接只筛选**事件**。要看具体投递，直接用投递列的状态徽标下钻：点击事件列表「投递」列的 `失败 2`，会打开 `/deliveries?eventId=<event-id>&deliveryState=failed`，列表只保留这一条 Event 当前失败的两条投递。逐条尝试记录再点通知目标名称进入。完整口径见[从事件下钻到具体投递](/operations/deliveries#从事件下钻到具体投递)。

搜索会忽略大小写，并将空白分隔的多个词按 **AND** 处理。例如 `checkout prod` 可以同时命中标题中的 `checkout` 和标签中的 `prod`；每个词可以出现在不同字段。最多使用前 8 个词。原始载荷与原始请求头不参与搜索。

常用检索示例：

| 目标 | 检索方式 |
| --- | --- |
| 找全部解析失败事件 | 搜索 `parse_failed`，或从解析失败提示进入同类事件 |
| 用通知里的 Event ID 反查 | 直接粘贴 Event ID |
| 用投递消息中的 Delivery ID 反查 | 在事件搜索中粘贴 Delivery ID |
| 用外部消息引用反查事件 | 粘贴目标平台返回的引用值，如飞书消息 ID `om_...`；命中产生该消息的事件 |
| 按告警身份追踪 | 搜索指纹值，再打开「同指纹」标签 |
| 查目标覆盖缺口 | 选择通知目标，并把「目标投递」设为“无该目标的投递” |

## 核对多目标投递覆盖

一条 Event 的邮件投递成功、飞书投递失败时，「投递结果」选成功或失败都会找到它。要先区分扇出是否完整送达，在事件页打开「筛选」，使用「投递覆盖」：

| 界面选项 | URL 值 | 匹配条件 |
| --- | --- | --- |
| 全部送达 | `deliveryCoverage=all` | 至少有一条 Delivery，且全部当前为 `succeeded` |
| 部分送达 | `deliveryCoverage=partial` | 至少一条当前为 `succeeded`，同时至少一条不是 `succeeded` |
| 无人送达 | `deliveryCoverage=none` | 至少有一条 Delivery，且没有任何一条当前为 `succeeded` |

`pending`、`running`、`failed` 和 `suppressed` 都按未送达计算。因此，一条成功加一条待处理属于「部分送达」；全部仍在排队、全部失败或全部被静默都属于「无人送达」。这些结果的原因不同，不能只凭覆盖筛选决定重试。它读取当前状态：失败投递重试成功后，事件可能从「部分送达」变为「全部送达」，早期失败仍需到尝试记录中核对。

::: warning 全部送达只核对现存投递
覆盖按该 Event 的**全部现存 Delivery**判断，即使选择了通知目标，也不会只计算该目标。它不检查本应接收却没有创建 Delivery 的目标；同一目标被多条路由选中时，每条 Delivery 都参与判断。`succeeded` 表示 Tocsin 按适配器规则记录目标已接受，不证明值班人员已读，也不代表电话加急已成功。指定目标是否缺失仍用[目标投递筛选](#目标投递结果怎么组合)，呼叫结果见[飞书应用与电话加急](/integrations/feishu-app)。
:::

### 区分无人送达与无投递

完全没有 Delivery 的事件不属于上述三类。它可能未命中路由，也可能因去重或记录删除而没有现存投递，需要打开[路由匹配证据](#读取路由匹配证据)确认原因。

- 「投递覆盖 → 无人送达」对应 `deliveryCoverage=none`：有投递，当前成功数为 0。
- 「投递结果 → 未产生投递」对应 `deliveryOutcome=none`：当前没有任何投递。

两项按 AND 组合时没有结果，因为一项要求有投递，另一项要求没有投递。要扫描最近 1 小时无人送达的事件，使用：

```text
/events?deliveryCoverage=none&range=1h
```

若还要查完全没有投递的事件，清除投递覆盖，再将投递结果设为「未产生投递」。

### 从部分送达下钻处置

覆盖与投递结果、目标投递结果、告警源、严重程度和时间范围等条件按 AND 组合。例如，找最近 1 小时已有部分成功、同时确实存在终态失败投递的事件：

```text
/events?deliveryCoverage=partial&deliveryOutcome=failed&range=1h
```

如果只选「部分送达」，成功加待处理、运行中或已抑制的组合也会返回。定位事件后，点击投递列对应状态徽标下钻：`failed` 先核对错误与目标端是否已受理，再决定是否重试；`pending` / `running` 检查退避、暂停与滞留；`suppressed` 核对静默规则。处置细节见[投递状态与时间口径](/operations/deliveries#状态与时间口径)和[手动重试](/operations/deliveries#手动重试)。

覆盖只用于事件列表。用页内入口切换到投递列表时不会携带 `deliveryCoverage`；要保持同一事件的范围，使用该行的投递状态徽标，而不是直接切换列表。点击「投递覆盖」chip 只清除覆盖条件，修改覆盖会回到第一页。

## 解析失败事件

Provider 拒绝 Webhook 载荷时，Tocsin 仍会保存一条用于审计的 Event，并返回带 `eventId` 的 `400`。这类事件在列表中显示「解析失败」徽标，详情页顶部会显示独立提示，而不是把它当成普通告警。

提示中可核对：

| 字段 | 含义 |
| --- | --- |
| 失败原因 | 载荷格式无效、载荷类型不受支持、告警源配置错误或解析器内部错误 |
| 错误类型 | Provider 解析器返回的错误类别 |
| 错误信息 | 已脱敏的诊断信息 |
| 载荷哈希 | 用于确认多次失败是否来自同一载荷 |

处理顺序通常是：先核对告警源是否选错 Provider，再检查上游是否改变了 JSON 结构，最后在「原始调试」查看已脱敏的原始载荷。修复后从上游重发一条代表性 Webhook，确认返回 `202` 且新 Event 不再显示解析失败。

## 解析结果筛选怎么用

「解析结果」是事件页专属的结构化筛选器，URL 参数是 `parseFailed=true|false`：

| 选择 | URL 值 | 返回的事件 | 适合回答的问题 |
| --- | --- | --- | --- |
| 解析失败 | `parseFailed=true` | Provider 在接入时拒绝告警载荷、但仍保存为审计 Event 的记录 | 上游是否开始发送 Tocsin 无法识别的载荷？ |
| 解析成功 | `parseFailed=false` | 没有解析失败标记的 Event，包括正常解析的告警，以及 Provider 元数据损坏或缺失、无法读出标记的旧记录 | 过滤掉已知的解析失败审计记录后，剩下哪些 Event？ |

例如，查看最近 24 小时的解析失败事件：

```text
/events?parseFailed=true&range=24h
```

「解析成功」选项只是排除条件，不是完整链路成功标志。它只表示列表行没有明确的 `parseFailed: true` 标记；正常解析的 Event 会在这里，但 Provider 元数据缺失或无法读取的旧记录也会在这里。对元数据可读的正常 Event，解析通过仍可能没有命中路由、没有创建 Delivery，或所有 Delivery 都失败。要区分这些情况，分别查看[路由匹配证据](#读取路由匹配证据)，再结合 `deliveryOutcome=none` 或[投递覆盖](#核对多目标投递覆盖)：

- `parseFailed=true` 且没有 Delivery：这是 Provider 拒绝载荷的审计记录，不要按未命中路由或去重缺口处理。详情顶部的解析失败提示和脱敏原始调试是第一证据。
- `parseFailed=false` 且 `deliveryOutcome=none`：当前 Event 没有明确解析失败标记，也没有任何 Delivery。对元数据可读的正常 Event，这通常表示载荷已通过解析但没有命中路由；打开路由匹配快照，排除路由/目标状态变化、幂等去重或证据清理。它不等同于 parser 拒绝。
- `parseFailed=false` 且有失败或无人送达投递：当前 Event 没有明确解析失败标记，问题在已经创建的 Delivery 链路；对元数据可读的正常 Event，解析已完成。下钻 Delivery 查看尝试记录和目标回执。

`false` 还会保留 Provider 元数据缺失或损坏的旧 Event，因为事件列表的筛选和列表行投影都按“无法读出明确 `parseFailed: true` 就不是解析失败”处理。这保证一条损坏的元数据不会让事件列表或分页消失，但也意味着 `parseFailed=false` 不能证明旧 Event 的解析过程曾经成功；详情读取会严格解析 Provider 元数据，损坏的 JSON 可能导致详情无法加载。需要时以规范化字段、路由快照和投递记录交叉核对。解析失败 Event 的字段含义和修复顺序见[解析失败事件](#解析失败事件)。

## 读取路由匹配证据

「路由匹配」标签会列出事件接入时评估过的路由。每行包含路由结果、目标数量、投递结果和逐项条件检查。

先看标题下方的来源说明：

- **接入时刻记录**：事件保存了当时的匹配快照，反映接入时生效的路由，不会被当前规则改写。
- **读时重算**：旧事件没有快照，页面按当前路由重新计算。这不是接入时的结论，修改规则后再打开页面，结果可能变化。

逐项检查会同时展示规则期望值与事件实际值。先确认 Source、severity、status、label、title 或 message 是否按预期匹配，再判断 Delivery 为什么存在或缺失。

如果路由结论是命中但没有投递，「未投递的原因」会区分为：

| 原因 | 运维含义 |
| --- | --- |
| 路由已停用 | 匹配快照显示命中，但路由当前已停用，不再允许产生新投递 |
| 路由已删除 | 路由的投递记录随删除级联清理 |
| 通知目标已停用 | 匹配快照包含该目标，但当前缺少对应 Delivery，且目标现在已停用；这是缺口读取时的目标状态，不代表停用会阻止入队，正常接入仍会创建 `pending` Delivery |
| 通知目标已不存在 | 路由仍引用了一个已删除目标 |
| 同一窗口内重复 | 相同幂等键与目标已在去重窗口内投递；如果首发事件仍在记录中，可直接点开 |
| 无法复原 | 解释原因所需的记录已过期或被清理 |

没有命中任何路由时，事件仍保留，但不会创建 Delivery。需要让历史事件走当前规则时，使用下一节的「重新匹配」；不要把它和 Delivery 的手动重试混为一谈。

## 查看通知投递

「投递」标签列出该事件产生的所有 Delivery。目标名称可进入 Delivery 详情；在那里继续核对状态、尝试次数、下次重试时间、渲染载荷、目标回执与错误。

事件列表「投递」列的状态徽标是同一个扇出的快捷入口：每个非零状态徽标都链接到已按该 Event 与状态收窄的投递列表。没有任何投递、也没有匹配中的路由记录时显示「未匹配路由」；有命中记录却没有任何投递时显示不可点击的 `0`，原因通常是幂等去重、并发配置变化或证据已被清理。目标停用通常仍会创建 `pending` Delivery，只是 Worker 暂不领取。徽标计数读取当前状态，重试成功后的投递不再计入失败。

### 两个「未匹配路由」不是同一个口径

事件列表中的「未匹配路由」和告警源列表中的同名徽标回答不同问题，不能互相替代：

| 位置 | 判断的问题 | 数据时点与含义 |
| --- | --- | --- |
| **事件列表** | 这条 Event 接入时有没有命中路由？ | 对有接入快照的 Event，读取当时保存的路由匹配结果；只有匹配路由数为 `0` 且当前没有任何 Delivery 时才显示「未匹配路由」。没有快照的旧记录在列表中按 `0` 个匹配处理，详情页会标注按当前路由重算；有快照的结果不会因后来修改路由而改写。 |
| **告警源列表** | 这个告警源按当前配置有没有路由覆盖？ | 读取当前启用路由的静态覆盖计算。没有任何启用路由覆盖该告警源时显示「未匹配路由」；`rule.sourceIds` 为空的兜底路由也算覆盖，不需要先产生 Event。详见[告警源列表的路由覆盖](/guide/sources#在列表中核对路由覆盖)。 |

事件列表显示不可点击的 `0` 时，说明接入快照中有命中路由，但当前没有对应 Delivery；应打开 Event 的[路由匹配证据](#读取路由匹配证据)，先区分幂等去重、路由删除或并发配置变化，以及证据是否已清理。通知目标停用本身通常只会让既有或新建的 Delivery 保持 `pending`，不会把数量变成 `0`。即使事件有一条投递，也不代表每个通知目标都收到；目标侧的当前配置覆盖见[通知目标列表的投递路由](/integrations/destinations#在列表中核对投递路由)。

投递列表检索、状态、自动退避、手动重试和积压处置见[投递检索、生命周期与重试](/operations/deliveries)，徽标链接的参数与清除方式见[从事件下钻到具体投递](/operations/deliveries#从事件下钻到具体投递)。若 Delivery 为 `suppressed`，说明它命中了静默规则或维护时段，并不代表发送失败；具体规则见[告警静默与维护时段](/operations/suppressions)。

## 判断是否重复发生

「同指纹」标签回答“同一个告警是否又来了”：

- 统计范围是同一告警源、完全相同 fingerprint 的更早事件。
- 页面显示更早出现次数、最近一次时间、与上一次相比的字段和标签变化。
- 最近记录最多显示 5 条，可直接打开对应事件。
- 汇总区提供两个下钻入口：在事件列表查看全部出现次数，以及在投递列表查看该指纹发出的全部投递
  （同样限定同一告警源、完全相同 fingerprint）。两者都是精确等值匹配，不会掺入正文碰巧包含
  同一串字符的其它告警。
- 首次出现时显示空态，不会把它误报成历史问题。

fingerprint 只在产生它的告警源和 Provider 语义内有意义，不会跨 Source 聚合。该标签也不是 incident 分组或趋势图。

## 原始调试与保留策略

「原始调试」显示服务端脱敏后的原始载荷和请求头。`rawPayload` 适合确认上游实际发送了什么，但不应替代标准化字段做路由判断。

原始数据尚未清理时，页签会显示保留截止时间；超过窗口但清理尚未运行时，会明确提示等待后台处理。清理后页面显示“原始数据已按保留策略清理”，而不是把内部占位值渲染成上游 JSON。标准化字段、路由匹配快照与 Delivery 仍可继续用于排障。清理触发时机、`0` 天语义、历史表增长与 SQLite 空间判读见[数据保留与 SQLite 容量](/operations/data-retention)。

原始载荷和请求头不参与事件搜索。不要把 Token、Cookie、Authorization Header 或包含凭据的调试响应复制到公开工单和聊天记录。

## 下载事件证据包

事件详情工具栏的「下载证据包」会生成一份 JSON 快照，文件名形如：

```text
tocsin-event-<event-id>-<UTC timestamp>.json
```

顶层结构如下：

```json
{
  "schemaVersion": 1,
  "kind": "event",
  "subjectId": "event-...",
  "exportedAt": "2026-10-28T04:00:00.000Z",
  "event": {}
}
```

`event` 字段包含当前操作者本来就能在详情页看到的完整 DTO。导出前会再次执行脱敏，避免字段名或自由文本中的凭据形态泄露；它不会扩大可见范围，也不会找回已经清理的原始数据。

证据包适合附到事故工单或交给同事复核，但它仍可能包含内部主机名、标签和已脱敏的原始载荷。对外共享前应按组织的数据分类要求再检查。

## 重新匹配与补投

「重新匹配」不是重试已有 Delivery。它按**当前已启用的路由和当前规则**重新评估事件，只为缺失的“路由 + 通知目标”组合创建 Delivery。

确认前先在预览中检查：

- 命中了多少条当前路由。
- 哪些目标是“新建”，哪些已存在对应 Delivery。
- 最终会新建多少条投递，以及是否会跳过已有目标。

已有目标不会重复创建；没有新目标时确认按钮不可用。确认后投递只是入队，仍要由进程内 Worker 异步发送。若全局投递已暂停，恢复后 Worker 才会继续处理。

适用场景是“事件已经恢复，但当时路由没有配置正确，目标后来才补上”。如果目标已经成功接收消息、只是成功状态没有落库，不要用重新匹配盲目重发，以免产生重复通知。
