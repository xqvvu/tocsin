# 告警源接入与生命周期

告警源（Source）代表一个独立的上游发送方。它把固定的 Webhook 入口、认证凭据、Provider 解析器和启停状态绑定在一起，并决定新请求会以哪个上游身份进入 Event → Route → Delivery 链路。

为每个上游系统或独立发送职责创建一个告警源。不要让多个无关系统共用一个接入 Token，否则无法独立轮换、停用或审计。

## 每个告警源包含什么

| 项目 | 运维含义 |
| --- | --- |
| Source ID 与 Webhook URL | 稳定的接入地址：`/api/sources/<source-id>/webhook`。轮换 Token 不会改变 URL。 |
| 接入 Token | 每个告警源独立的 bearer 凭据。服务端只保存哈希，明文只在创建、轮换或导入新 ID 时一次性显示。 |
| Provider | 选择与上游请求体一致的告警解析器；解析结果会写入 Event 的规范化字段。 |
| 额外共享密钥 | 可选的第二个 Tocsin 侧固定凭据，通过 `X-Tocsin-Provider-Secret` 发送。它不是上游原生 HMAC 验签。 |
| 启停状态 | 停用后拒绝新的 Webhook，但不会删除现有 Event、Route 或 Delivery。 |

Token 不能再次查看。告警源列表可以重新复制 Webhook URL，但不会重新显示 Token；丢失或怀疑泄露时应轮换。

## 创建并验证接入

1. 在「告警源」选择与上游载荷匹配的 Provider，并填写值班人员能辨认的名称。
2. 按需设置额外共享密钥。只使用接入 Token 时留空即可。
3. 创建后立即保存一次性显示的 Webhook URL 与接入 Token。两者都能从提示中复制，Token 也可手动选中。
4. 在上游系统填入 URL 与任一已配置凭据，并以 `application/json` 发送一条代表性测试载荷。
5. 确认返回 `202`，再检查 Event 的规范化字段和 Route 匹配证据。`202` 只表示接入成功，不表示目标已送达。

接入认证接受以下任一有效凭据：

| 凭据 | 请求头 |
| --- | --- |
| 接入 Token | `Authorization: Bearer <source-token>` |
| 接入 Token | `X-Tocsin-Source-Token: <source-token>` |
| 额外共享密钥 | `X-Tocsin-Provider-Secret: <shared-secret>` |

dashboard 登录 session 不能用于 Webhook。未配置额外共享密钥时，该请求头不能替代 Token。字段样例与响应码见[告警源接入参考](/integrations/providers)。

::: tip 先验证再上路由
先确认测试请求产生 Event，再创建或启用 Route。这样能把“认证或解析失败”和“路由没有命中”分开排查。如果暂时不希望写入 Event，可先用[接入预演](#接入预演)验证解析、路由与投递判定。
:::

## 在列表中核对路由覆盖

「告警源」列表的「命中路由」列按当前配置静态推算每个告警源能否投递，不需要先发一条真实告警。它读取已启用的路由和通知目标，不读取历史 Event 或 Delivery。

- `N 条可投递`：N 条已启用的路由覆盖该告警源，且每条至少关联一个已启用的通知目标。
- `M/N 条可投递`：共 N 条覆盖路由，只有 M 条能投递；其余路由的目标全部停用或已不存在。
- `目标全停用`：有启用的路由覆盖该告警源，但没有任何一条能投递；投递会入队并保持待发送。
- `未匹配路由`：没有已启用的路由覆盖该告警源。
- `… · N 条带条件`：在上面的可投递路由中，有 N 条还要求事件满足条件才会转发。

计数口径：

- **覆盖**要求路由已启用，并且路由的告警源条件为空（兜底路由，对所有告警源生效）或包含当前告警源。停用的路由不参与任何计数。
- **可投递**要求路由至少关联一个已启用的通知目标。目标被删除与停用同样处理；同一路由下其它停用的目标不在本列单独提示，到[路由列表](/guide/routes)查看「N 个目标已停用」。
- **带条件**指路由还填写了严重程度、状态、标签、标题包含或消息包含中的任意一项；只选择告警源不算条件。条件路由只有在可投递时才追加该后缀，目标全部停用时只计入阻断口径。

悬浮徽标可以查看明细：可投递时列出路由名，以及其中多少条指定告警源、多少条兜底；部分阻断时列出目标不可用的路由；带条件时补充这些路由的名称。

::: warning 覆盖不等于全量送达
`N 条可投递` 只说明有 N 条路由的配置允许发送，不表示该告警源的每条告警都会发出通知。带条件后缀的路由只转发满足条件的告警；即使没有任何后缀，[静默](/operations/suppressions)、[全局投递暂停](/operations/settings#投递急停)、幂等去重和目标端故障也可能让投递终止或延后。
:::

该列是配置视图，不评估静默、暂停、去重和历史送达率。要确认某条具体告警的去向，看 Event 详情的[路由匹配证据](/guide/routes#查看匹配证据)；切换上游流量前，先用[接入预演](#接入预演)回放代表性载荷，预演会额外给出静默、目标停用与全局暂停的投递判定。

### 覆盖异常的处置

| 看到 | 先做什么 |
| --- | --- |
| `未匹配路由` | 新建路由并选择该告警源，或启用已有路由；兜底路由也会覆盖它 |
| `目标全停用` | 启用路由关联的任一目标，或把路由改到可用目标；重启 Worker 不能解决该问题 |
| `M/N 条可投递` | 悬浮确认被阻断的路由，逐条恢复目标或调整路由 |
| `· N 条带条件` | 打开这些路由核对条件；如果意图是接收该告警源的全部告警，补一条无条件路由或放宽条件 |

## 接入预演

「接入预演」把一段上游 Webhook 请求体按**当前已保存**的解析器与路由规则回放，用于在切换上游流量前确认解析字段、路由命中、目标渲染，以及每个目标此刻的真实投递判定。入口在「告警源」页工具栏，与「新增告警源」并排；选择告警源、粘贴 JSON 请求体后运行。

结果分为三段：

| 结果 | 内容 |
| --- | --- |
| 解析结果 | 规范化后的严重程度、状态、标题、消息、指纹、发生时间与标签。解析失败时显示原因和脱敏后的错误信息。 |
| 路由判定 | 当前每条路由一行，显示是否命中、该路由配置的目标数与逐项条件证据。停用的路由会因启用条件未通过而显示未命中。 |
| 目标渲染预览 | 命中路由关联的每个通知目标会渲染出的通知内容，以及该目标的投递判定与静默规则。已停用的目标仍会渲染并标注「已停用」。 |

### 读取投递判定

每个目标的渲染结果都带一条判定，说明按**预演时刻**的静默规则、目标启停与全局投递开关，真实链路会走到哪一步。判定按真实链路的闸门顺序计算，先命中者生效：

- **`会被静默`**：预演时刻命中一条生效中的静默或维护时段规则。投递创建即成为终态 `suppressed`，不产生发送尝试；下方列出规则名、类型、原因与逐条件证据。
- **`目标已停用`**：命中路由关联的目标当前停用；目标已被删除时同样显示停用并给出未找到原因。投递不会被 Worker 领取，直到目标重新启用。
- **`排队等待恢复`**：未命中静默、目标启用，但实例级「暂停出站投递」已开启。投递进入队列但不会被领取，恢复后按队列顺序继续。
- **`会送达`**：没有静默命中、目标启用、全局投递未暂停。入队后由 Worker 正常发送。

`会被静默` 的明细来自与真实入队相同的判定逻辑：规则名、类型（`维护时段` 或 `临时静默`）、可读原因，以及与路由匹配相同的逐条件证据；检查值在服务端脱敏后才返回。全局投递暂停时，结果顶部还会显示「全局投递已暂停」提示条和暂停开始时间。

判定与渲染是否成功分开显示：渲染报错说明目标配置或模板无法为这段载荷生成内容；判定仍说明真实链路会走哪道闸门。两者都通过，才说明这条载荷在当前配置下可以正常投递。

预演是只读操作：不写入 Event、Delivery、投递尝试或加急队列，不创建后台任务，也不调用任何通知目标的发送接口，也不会因为判定而改变任何规则或队列状态。

### 预演的边界

| 边界 | 说明 |
| --- | --- |
| 只回放请求体 | 不携带 HTTP 请求头，也不校验 Webhook URL、接入 Token、额外共享密钥或网络可达性；认证与 `202` 响应仍要用真实请求验证。 |
| 使用已保存配置 | 编辑框中尚未保存的 Provider、共享密钥或路由修改不参与本次回放。 |
| 判定时刻 | 投递判定只使用服务端执行预演的时刻：只有当时生效中的静默规则参与判定，尚未开始或已经结束的维护时段不参与，也不回放历史静默命中记录。 |
| 判定不是送达回执 | 「会送达」只表示通过静默、目标启停和全局暂停三道闸门；幂等去重、目标端故障和网络问题仍可能让投递失败或延后。 |
| 请求体格式与上限 | 必须是合法 JSON；按序列化后的字符数计算，上限 `262144` 个字符（约 256 KiB），超限会在服务端被拒绝。 |
| 不保留历史 | 不保存预演记录，也不支持按历史 Event 重放；需要留档时自行保存载荷和结果。 |
| 停用的告警源 | 仍可预演，便于恢复前确认载荷；但真实 Webhook 会返回 `403`。 |
| 需要登录 | 预演要求 dashboard 登录 session，不能代替上游 Webhook 的告警源 Token。 |

解析失败的原因分为：请求体无效（所选 Provider 不接受这段 JSON 的结构或必填字段）、请求体暂不支持（上游事件类型不在 Provider 支持范围内）、告警源配置错误（保存的解析器配置本身校验失败，与载荷无关）。

### 常见用法

- **首次接入**：粘贴上游的一条代表性载荷，确认标题、级别、状态与标签符合预期，判定为「会送达」后，再按[Provider 接入验收配方](/integrations/provider-verification)发送真实请求并核对 `202`。
- **切换 Provider**：先用目标解析器支持的载荷预演，确认字段后再保存并更新上游。
- **调整路由**：同一段载荷重复预演，逐条核对条件证据，判断路由命中和拒绝的原因。
- **核对静默覆盖**：维护时段生效期间预演代表性载荷，确认判定为「会被静默」并核对规则名与条件证据；如果期望某条投递不被静默，这是发现条件过宽的最快方式。
- **核对投递急停**：暂停出站投递期间预演，确认判定为「排队等待恢复」，避免把“已入队”误读成“已发送”；恢复步骤见[设置与运行态操作](/operations/settings#投递急停)。
- **调试解析失败**：真实 Webhook 解析失败会写入一条 `parse_failed` Event；预演不会。适合在不污染事件历史的情况下反复调整载荷。

## 轮换接入 Token

轮换会为同一个告警源生成新 Token，并立即替换旧 Token 的哈希。Source ID、Webhook URL、Provider、Route 和 Event 历史都不变。

::: warning 没有新旧 Token 并行宽限期
轮换提交后，旧 Token 立即无法通过认证。新 Token 只在完成轮换后的提示中显示一次。
:::

推荐按以下顺序操作：

1. 确认上游系统支持快速更新 HTTP 认证凭据，并通知相关值班人员。
2. 如果上游使用额外共享密钥，可先确认该凭据仍能独立通过认证，避免 Token 切换中断。Token 与共享密钥任一有效即可。
3. 在告警源行执行「轮换接入 Token」并确认。
4. 立即保存新 Token，更新上游认证配置，然后发送测试请求。
5. 确认收到新 Event，不应再使用旧 Token 做重试或排障。

轮换 Token 不会修改额外共享密钥；更换共享密钥也不会自动轮换 Token。若两者都可能泄露，应分别处理并更新上游。

## 停用与重新启用

停用告警源会先于凭据校验拒绝新的 Webhook，因此 Token 或共享密钥正确也会返回 `403`。停止期间不会创建 Event，也不会有新的 Route 匹配或 Delivery。

- 已入队的 Delivery 会继续由 Worker 发送；停用告警源不是出站投递的总开关。
- 重新启用后，原有 Token 和额外共享密钥继续生效，无需重新生成。
- 如果仍需要记录 Event、但暂时不希望发送通知，应使用[告警静默与维护时段](/operations/suppressions)，而不是停用告警源。
- 告警风暴中停用告警源与其他急停手段的取舍，见[告警风暴与大面积误报的处置顺序](/operations/incident-playbook)。

停用确认框会显示当前排队中的 Delivery 数，便于在拒绝新告警前判断是否仍有在途通知。

## 编辑解析器或共享密钥

编辑告警源可以改名、切换 Provider 或覆盖额外共享密钥。

- Provider 或共享密钥变更只影响后续 Webhook；历史 Event 的规范化结果和路由匹配快照不会重算。
- 编辑框中的共享密钥留空表示保留当前值。输入新值会覆盖旧共享密钥；新凭据保存后应立即更新上游。
- 切换 Provider 前，先用目标解析器支持的示例载荷验证，避免新请求只生成解析失败 Event。

## 删除告警源

删除是不可撤销的破坏性操作。删除告警源会同时移除它的接入 Token、共享密钥、Event 和关联 Delivery；只引用该告警源的 Route 也会被删除，仍引用其他告警源的 Route 只会收窄条件。

删除确认框会列出：

- 可能连带删除的路由数；
- 只移除当前告警源引用、继续保留的路由数；
- 将随 Event 级联删除的历史记录影响。

需要保留审计历史时，优先停用告警源，而不是删除。确认上游已经停止发送后，再按团队的事件保留和备份策略执行删除。

## 故障与凭据处置清单

| 现象或任务 | 处理 |
| --- | --- |
| 新 Webhook 返回 `401` | 确认 URL 中的 Source ID、Token 位置和额外共享密钥是否与当前配置一致；不要尝试从 dashboard 找回旧 Token。 |
| 新 Webhook 返回 `403` | 检查告警源是否已停用；重新启用后沿用原凭据。 |
| Token 丢失 | 直接轮换 Token，保存新值并更新上游。 |
| Token 或共享密钥泄露 | 立即替换对应凭据，检查近期 Event 和 Delivery，并按事故流程处理备份与日志暴露范围。 |
| 上游切换完成但 dashboard 没有 Delivery | Event 可能存在但 Route 未命中或目标停用；见[故障排查](/operations/troubleshooting)。 |
