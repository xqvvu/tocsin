# 路由规则与匹配

路由（Route）决定一个 Event 要投递到哪些通知目标。匹配结果只取决于 Event 的规范化字段、路由条件和启停状态，不按规则优先级或列表顺序裁决。

需要暂停整个上游接收时，[停用告警源](/guide/sources#停用与重新启用)；需要暂停某个通知渠道时，停用通知目标；需要在一段时间内跳过一组明确的告警时，使用[告警静默与维护时段](/operations/suppressions)。这样 Event 与路由匹配证据仍可审计，避免把“未收到告警”和“收到后按规则静默”混为一谈。

## 创建一条路由

先在「通知目标」创建并测试至少一个目标，再到「路由」选择「新增路由」。

1. 填写可辨认的路由名称，例如 `Prod critical to on-call`。
2. 按需添加告警源、严重程度、状态、标签、标题包含和消息包含条件。
3. 选择一个或多个通知目标。
4. 保存并启用路由。

每一类条件可以不填。未填写的条件类别不限制匹配；如果所有条件类别都为空，这条路由会匹配全部 Event，保存前会出现二次确认。

### 条件组合规则

| 条件 | 多选时的含义 | 空值 |
| --- | --- | --- |
| 告警源 | 命中列表中的任一告警源 | 不限制告警源 |
| 严重程度 | 命中列表中的任一严重程度 | 不限制严重程度 |
| 状态 | 命中列表中的任一状态 | 不限制状态，包括 `unknown` |
| 标签 | 每条标签条件都必须同时满足 | 不限制标签 |
| 标题包含 | 每个子串都必须出现在标题中 | 不限制标题 |
| 消息包含 | 每个子串都必须出现在消息中 | 不限制消息 |

不同条件类别之间按 **AND** 组合；同类下拉多选按 **OR** 组合。标签的“等于”和“包含”区分大小写；标题与消息的“包含”不区分大小写。规则不支持正则表达式、glob 或任意表达式。

例如：

| 字段 | 配置 |
| --- | --- |
| 告警源 | Grafana 生产环境 |
| 严重程度 | `critical`、`warning` |
| 状态 | `firing`、`resolved` |
| 标签 | `environment=prod`、`service contains checkout` |
| 标题包含 | `Checkout` |
| 通知目标 | 飞书值班群、Slack SRE 频道 |

只有同时来自该告警源、严重程度为 `critical` 或 `warning`、状态为 `firing` 或 `resolved`、两个标签和标题条件都满足时才命中；命中后会为两个通知目标各创建一条 Delivery。

::: warning 状态条件会缩小恢复通知
状态留空表示触发、恢复和未知状态都匹配。一旦选择状态，未选中的状态就不会命中。界面会在缺少 `firing` 或 `resolved` 时提示，路由列表也会显示「不含触发中」「不含已恢复」或「不含触发与恢复」，避免出现“告警会发、恢复不发”或相反情况。
:::

## 匹配、顺序与去重

- **没有优先级和首条命中短路。** 一条 Event 可以同时命中多条已启用路由；每条命中的路由都会按自己的通知目标创建 Delivery。重复幂等键或同一 Event 上已存在的目标组合会被跳过。
- **列表排序不影响路由。** 路由表按展示需要排序，不参与匹配裁决。
- **停用路由不参与新匹配。** 已有但尚未发送的 Delivery 会暂停；重新启用后继续，启用前会确认并披露当前积压数。停用不会删除历史 Event 或投递。
- **删除路由是破坏性操作。** 删除会同时删除该路由关联的 Delivery，但保留告警源接收到的 Event 和接入时的路由匹配快照。执行前先阅读界面的影响提示。
- **修改路由只影响后续匹配。** 已排队投递不会重新按新规则匹配；即使从路由中移除某个通知目标，已经创建的投递仍可能发往该目标。

短时间内的重复 webhook 还会经过幂等去重。去重键由告警源、幂等键、路由和通知目标共同组成，默认窗口为 5 分钟；幂等键通常来自请求载荷哈希或上游事件 ID。fingerprint 表示告警身份，不是投递幂等键，因此同一 fingerprint 的不同事件仍可能再次投递。

## 编辑、停用与删除

| 操作 | 对新 Event | 对已有 Delivery | 是否保留历史 |
| --- | --- | --- | --- |
| 编辑条件或目标 | 按新配置匹配 | 不重新匹配，按原投递目标处理 | 是 |
| 停用路由 | 不再命中 | 尚未发送的投递暂停，重新启用后继续 | 是 |
| 停用通知目标 | 路由仍可命中，但目标不发送 | 该目标的待发送投递暂停 | 是 |
| 删除路由 | 不再命中 | 关联 Delivery 一并删除 | Event 保留，路由匹配证据保留；Delivery 丢失 |

重新启用路由前，界面会先弹出确认框并显示该路由当前排队的投递数；确认后这些投递立即进入领取范围，但仍受通知目标启用状态、告警静默和全局投递暂停约束。

如果只是要临时安静一段时间，使用路由行的「临时静默此路由」或创建[告警静默](/operations/suppressions)，不要删除或停用配置。

### 告警源与通知目标的连带影响

| 操作 | 对路由 | 对投递 |
| --- | --- | --- |
| 停用告警源 | 路由保留，但 Webhook 请求被拒绝 | 已入队的投递继续发送 |
| 删除告警源 | 路由移除该来源；最后一个来源被移除时整条路由删除 | 路由删除时关联投递级联删除 |
| 停用通知目标 | 路由仍匹配，但无法向该目标发送 | 该目标的待发送投递暂停 |
| 删除通知目标 | 路由移除该目标；最后一个目标被移除时整条路由删除 | 关联投递级联删除 |

删除告警源或通知目标前，界面会给出「收窄 N 条路由」或「连带删除 N 条路由」的影响预览。通知目标侧的启用、停用与删除确认框还会列出受影响告警源、排队投递与积压的加急呼叫，口径见[启停与删除前的影响确认](/integrations/destinations#启停与删除前的影响确认)。停用告警源是接收侧的变化，新请求返回 `403`，不会暂停已经在队列中的投递。路由列表还会标出无法触达的配置：「无告警源」「告警源已停用」以及已停用的通知目标。

## 查看匹配证据

Event 详情中的「路由匹配」会展示命中与未命中的路由、每个条件的期望值和 Event 实际值，以及“命中但未创建投递”的解释。

这里是逐条 Event 的判定证据。配置层还有两份静态口径：告警源列表的「命中路由」列回答这个告警源能否投递，见[告警源列表的路由覆盖](/guide/sources#在列表中核对路由覆盖)；通知目标列表的「投递路由」列回答哪些启用路由会投递到该目标，见[通知目标列表的投递路由](/integrations/destinations#在列表中核对投递路由)。两者都只读当前配置，不读取历史 Event 或 Delivery。

- **接入快照**是 webhook 到达时记录的证据，不随之后修改路由而变化。
- **现状重算**表示旧 Event 没有接入快照，页面按当前路由计算；它不能证明事件到达时命中了该路由。
- 路由快照显示命中但没有 Delivery 时，检查路由是否已停用、目标是否已停用或删除、是否被幂等去重，或证据是否已被清理。目标停用通常不会阻止接入时创建 Delivery；它会让新建或已有的 Delivery 保持 `pending`，因此应把“目标已停用”理解为当前缺口状态，而不是零投递的唯一原因。
- 被静默的投递会以 `suppressed` Delivery 出现，不属于“命中但未投递”的缺口。

「命中但未投递」的常见原因：

| 原因 | 含义 |
| --- | --- |
| 路由已停用 | 路由已停用，接入时未投递 |
| 目标已停用 | 该目标已停用 |
| 目标已不存在 | 该目标已不存在 |
| 路由已删除 | 该路由已被删除，其投递记录随之级联删除 |
| 重复告警 | 同一告警已就该路由与目标投递过；仅在去重窗口内可解释 |
| 无法复原 | 该路由没有投递记录，且原因无法从保留的记录中复原 |

去重原因只在窗口内可解释，窗口过后会退化为「无法复原」。

「预览历史匹配」用于检查最近 Event 中还有哪些目标缺少 Delivery，并可确认后补投候选事件：

- 控制台当前扫描最近 20 条事件；只对已启用路由开放，停用路由不能预览或补投。
- 确认后只为缺失的路由与目标组合创建投递；已有投递不会重复创建，包括失败或 `suppressed` 的投递。
- 补投使用补投时刻的路由与目标配置，不会改写 Event 的接入快照；投递详情会标注“接入时快照中没有这条路由——补投按补投时刻的规则评估”。
- 它不是规则试跑器，不会重新匹配全部历史，也不能替代投递重试：失败投递应在详情页重试，被静默的投递需要等待新 Event。

## 路由与静默的边界

路由先决定“这条 Event 应不应该产生投递”，静默随后决定“已经产生的投递现在要不要发”。因此：

- 命中的静默不会修改 Event，也不会删除路由匹配快照。
- 被静默的 Delivery 会以 `suppressed` 出现在投递历史中，不应该与“路由未命中”混为一谈。
- 删除或停用路由会影响投递本身；临时停止通知应使用[告警静默与维护时段](/operations/suppressions)。

## 操作检查清单

1. 用可辨认的名称说明投递意图，例如 `Prod critical to on-call`。
2. 明确选择状态；需要恢复通知时不要漏掉 `resolved`。
3. 确认目标已启用，并检查路由表里的告警源可达性和状态范围提示。
4. 发送一条代表性告警，核对 Event 的逐条件匹配证据与每个目标上的 Delivery。
5. 计划变更期间优先创建静默，不要在事后才通过删除路由解释“为什么没有通知”。
